# 智能填单表单桥接实施说明

更新时间：2026-08-28

> 目标：在不购买 `cbf 多渠道对话框架`、不修改浪潮原生部署包的前提下，让环宝智能助手生成的结构化字段真正写入 iGIX 运行中的业务表单。
>
> 本文是实施设计和执行手册，不是对浪潮授权能力的绕过方案。真正上线前，必须先在一个测试表单上完成真实浏览器验收。

## 一、先说结论

`rtcommon / fillform` 不能完成真正的字段回填。

服务器上的原生包 `/platform/runtime/common/web/fillform/fillformwidget.js` 公开了 `window.FillformWidget`，但它的职责只有三件事：

1. 接收外部传入的 `data`；
2. 把 `data.fields` 渲染成字段名和值；
3. 点击打开菜单，使用 `gspframeworkService.rtf.func.openMenu` 打开业务页面。

它没有表单实例、没有 `input.value` 写入、没有 `BindingData`、没有模型调用，也没有字段赋值接口。因此，不能把字段数组传给 `fillform` 后就认为表单已经填写完成。

真正可行的方案是增加一个表单侧桥接器：

```text
环宝助手
  -> 结构化字段、用户确认
  -> 门户父页面校验并打开真实表单
  -> 真实表单中的桥接器接收字段
  -> BindingData.setValue 写入表单状态
  -> 表单桥接器返回 ACK
  -> 环宝助手根据 ACK 显示已回填、部分回填或未回填
```

第一版必须把真实字段回填做成硬验收项。只有看到真实表单字段显示新值，并且收到表单桥接器的成功回执，助手才可以显示已回填。没有回执时只能显示表单已打开或等待人工填写。

### 2.2 iGIX 运行时的打开和参数传递能力

服务器文件：

```text
/home/GSCloud/web/platform/runtime/common/web/gsprtf/gsp.rtf.core.js
```

运行时公开接口最终委托给框架适配器：

```js

gspframeworkService.rtf.func.openForm(options)
gspframeworkService.rtf.func.getEntityParam(tabId, callback, isSubonce)
```

`openMenu` 本身只负责打开菜单和传递 `entityParams`，并不负责向目标表单控件写值。

运行时页签 ID 会把 `funcId` 和 `tabId` 合并，形式类似：

```text
<funcId>_<tabId>
```

因此，桥接请求必须带自己的 `requestId`，不能只依赖业务数据 ID，否则多次打开同一个表单时容易串单。

运行时还会通过框架事件总线传递 `entityParams`。表单侧可以在实际环境验证后使用：

```js
window.gspframeworkService.rtf.func.getEntityParam(
  effectiveTabId,
  params => {
    // 读取本次打开表单携带的桥接标识
  },
  true
)
```

这个能力适合做打开参数的引导，但不能单独承担可靠回填，因为表单监听时机和页面初始化时机必须在真实环境验证。正式实现采用 ready、apply、ack 握手，事件总线只作为启动参数的辅助通道。

### 2.4 不需要维护全量菜单和字段映射

服务器上的智能填单配置模块还确认了两条动态发现链路：

```text
菜单：/api/runtime/sys/v1.0/functions/allFunctions
表单：/api/runtime/lcm/v1.0/rt-metadatas/helper?metadataTypes=Form,MobileForm
字段：/api/runtime/bcc/v1.0/aifillformConfig/form/{id}
```

因此，本项目不应把所有菜单和所有表单都抄进 `workflowActions.js` 或任何静态注册表。菜单候选应来自当前登录用户可访问的函数目录，表单字段候选应来自当前表单元数据或运行时字段描述。

原生智能填单确实会为一个新表单保存一条业务配置，配置内容包括可填字段、表单描述、菜单关系和智能体提示词。这是管理员确认业务边界，不等于开发人员为每个字段手写内部路径。

本桥接方案的目标应当调整为：

```text
平台动态提供菜单和字段技术信息
  -> 助手只生成当前表单字段 code 的值
  -> 桥接器根据当前运行时元数据校验
  -> BindingData.setValue 写入
```

只有字段存在业务歧义、需要特殊值转换或平台没有提供通用元数据入口时，才增加小范围别名或兼容配置。

## 三、为什么不能直接改输入框

禁止使用以下方式作为正式实现：

```js
document.querySelector('input[name="projectName"]').value = value
```

原因很具体：

- 可能只改了显示值，没有改 `BindingData`；
- 表单校验、脏值状态、变更集和保存动作感知不到这次修改；
- 组合表单、弹窗表单、虚拟控件和关联控件的 DOM 结构不稳定；
- 页面刷新或 Angular 重新渲染后，DOM 修改可能被覆盖；
- 跨 iframe、跨域和组件封装会让选择器失效；
- 关联人员、组织、枚举、日期等字段通常不是一个字符串就能表达。

DOM 修改可以作为临时探查手段，不能作为生产能力，也不能作为验收依据。

## 四、正式架构

### 4.1 三方职责

#### 环宝助手 iframe

负责：

- 识别用户意图；
- 调用现有 Dify 或项目模型生成结构化字段；
- 获取当前登录用户的白名单信息；
- 展示字段预览；
- 等待用户确认；
- 向门户父页面发送 `IGIX_AI_PREFILL_REQUEST`；
- 等待父页面转发的 `IGIX_AI_PREFILL_ACK`。

不负责：

- 直接访问父页面的 `gspframeworkService`；
- 直接改目标表单 DOM；
- 自己猜测任意 `funcId` 或字段路径；
- 自动保存、提交、通过或驳回。

#### iGIX 门户父页面

负责：

- 校验助手 iframe 的 `event.origin` 和 `event.source`；
- 根据当前用户的函数目录或运行时上下文解析目标，不信任模型生成的 `funcId`；
- 保存待转发请求，分配页签和超时；
- 调用 `gspframeworkService.rtf.func.openMenu`；
- 将请求转发给目标表单 iframe；
- 校验目标表单来源并把 ACK 转回助手。

不负责：

- 自己操作目标表单字段；
- 把任意字段路径原样传给表单；
- 把发送 `postMessage` 当成字段已经写入。

#### 真实业务表单

负责：

- 在表单初始化完成后发送 ready；
- 校验请求 ID、当前表单身份、来源和运行时字段描述；
- 将已验证的字段 `code` 转换为当前表单的 `BindingData` 路径和值类型；
- 只允许可见、可编辑且通过类型校验的字段；
- 调用 `frameContext.bindingData.setValue`；
- 返回 applied、partial 或 rejected ACK；
- 不自动触发保存和提交。

### 4.2 请求协议

助手发送给门户父页面：

```js
{
  type: 'IGIX_AI_PREFILL_REQUEST',
  version: '1.0',
  payload: {
    requestId: 'uuid',
    formKey: 'runtime-derived-or-optional',
    fields: [
      {
        key: 'projectName',
        label: '项目名称',
        value: '德国出差项目',
        valueType: 'text',
        source: 'user',
        confidence: 0.98
      }
    ],
    expiresAt: 0
  }
}
```

请求中的 `formKey` 应由当前表单上下文、菜单目录或兼容配置确定，不能由模型自由指定。`fields[].key` 优先使用当前表单元数据返回的真实字段 `code`；模型不能直接传入 `BindingData` 路径或任意 JavaScript。桥接器必须再次校验字段是否存在、可编辑以及值类型是否匹配。

### 4.3 打开表单时的参数

父页面查到白名单后，生成逻辑页签 ID，并把桥接标识放在 `entityParams`：

```js
const logicalTabId = `igix_prefill_${requestId}`

window.gspframeworkService.rtf.func.openMenu({
  appType: 'menu',
  funcId: formConfig.funcId,
  tabId: logicalTabId,
  appId: '',
  appEntrance: '',
  entityParams: {
    __igixPrefillBridge: '1.0',
    requestId,
    formKey: request.formKey
  }
})
```

父页面同时保存：

```js
pending.set(`${formConfig.funcId}_${logicalTabId}`, {
  requestId,
  formKey: request.formKey,
  fields,
  createdAt: Date.now(),
  expiresAt: Date.now() + 60_000
})
```

`entityParams` 只携带识别信息，字段本体由父页面的内存 pending 表保存并在目标表单 ready 后发送。这样可以避免字段过长时依赖 URL，也避免把未经确认的字段长期写入地址栏或 localStorage。

### 4.4 ready、apply、ack 握手

目标表单桥接器加载并确认 `BindingData` 已可用后，向门户父页面发送：

```js
{
  type: 'IGIX_AI_PREFILL_READY',
  version: '1.0',
  requestId: 'uuid',
  formKey: 'leave_request',
  funcId: '真实菜单标识',
  tabId: '真实页签标识'
}
```

门户父页面核对消息来源和 pending 记录后，向该表单 iframe 发送：

```js
{
  type: 'IGIX_AI_PREFILL_APPLY',
  version: '1.0',
  requestId: 'uuid',
  formKey: 'runtime-derived-or-optional',
  fields: [
    {
      key: 'projectName',
      label: '项目名称',
      value: '德国出差项目',
      valueType: 'text'
    }
  ]
}
```

表单桥接器逐字段调用 `BindingData.setValue`，然后返回：

```js
{
  type: 'IGIX_AI_PREFILL_ACK',
  version: '1.0',
  requestId: 'uuid',
  formKey: 'runtime-derived-or-optional',
  status: 'partial',
  appliedFields: ['projectName'],
  rejectedFields: [
    { key: 'travelCountry', reason: '当前元数据未提供可写值格式' }
  ]
}
```

状态定义：

| 状态 | 含义 | 助手显示 |
| --- | --- | --- |
| `applied` | 所有请求字段都已通过 `BindingData` 写入 | 已回填，请检查后提交 |
| `partial` | 一部分字段写入，一部分被拒绝 | 部分回填，请检查未完成字段 |
| `rejected` | 没有字段被写入 | 表单已打开，请人工填写 |
| 超时 | 表单未 ready 或没有 ACK | 未收到表单回执，请人工确认 |

没有 ACK，不能显示已回填。

## 五、表单侧实现方式

### 5.1 推荐方式：自定义业务组件或表单自定义控制器

不要直接修改服务器上的压缩部署包。应该在 iGIX 开发环境中做一个可复用的表单桥接能力，然后把它发布到需要支持智能填单的表单。

有两种实现方式：

1. 注册一个自定义业务组件，在表单设计器中拖入目标表单；
2. 如果当前版本允许表单自定义控制器，直接把桥接控制器挂到表单根组件的加载事件。

手册中自定义业务组件的关键元数据包括：

- `id`、`code`、多语言名称和图标；
- `control` 控件定义；
- `webControllers` 前端控制器信息；
- `businessEntityObject`；
- `businessEntityFields`；
- 控件事件到控制器命令的 `actionMapping`。

部署流程：

1. 创建并登记 `IgixPrefillBridge` 业务组件；
2. 实现桥接控制器；
3. 在表单设计器的自定义业务组件中找到它；
4. 先将组件拖入一个测试表单做 POC；
5. 让组件从当前表单运行时读取表单身份和字段描述，不把所有表单路径写死在组件里；
6. 只有特殊字段才配置少量别名、值转换或安全覆盖规则；
7. 保存表单；
8. 发布应用；
9. 刷新运行时并用真实浏览器测试。

如果当前版本只能把自定义组件编译进具体表单，仍然可以复用同一个桥接组件包。此时每个表单需要的是安装组件和完成一次运行时验收，不是重新编写一张字段映射表。

### 5.2 Angular 控制器代码骨架

下面是实现方向，不要不经检查就复制到所有表单。桥接器应该先从当前运行时取得字段描述，再使用字段 `code` 定位；每个表单仍要确认自己的根 `frameId`、元数据结构和特殊字段值格式。

```ts
import { Injectable } from '@angular/core'
import { BindingData, FrameContext } from '@farris/devkit'

type PrefillField = {
  key: string
  value: unknown
  valueType?: string
}

@Injectable()
export class IgixPrefillBridgeControllerService {
  private formKey = ''
  private fieldSchema = new Map<string, { path: string[]; dataType: string; editable: boolean }>()

  constructor(
    private readonly frameContext: FrameContext,
    private readonly bindingData: BindingData
  ) {}

  async onFormLoad(): Promise<void> {
    this.formKey = this.readCurrentFormKey()
    this.fieldSchema = this.readCurrentFieldSchema()

    // 只有在表单已完成初始化、BindingData 可用后才发送 ready。
    this.postToPortal({
      type: 'IGIX_AI_PREFILL_READY',
      version: '1.0',
      formKey: this.formKey
    })
  }

  applyFields(requestId: string, fields: PrefillField[]): void {
    const appliedFields: string[] = []
    const rejectedFields: Array<{ key: string; reason: string }> = []

    for (const field of fields) {
      const descriptor = this.fieldSchema.get(field.key)
      if (!descriptor) {
        rejectedFields.push({ key: field.key, reason: '当前表单元数据中不存在该字段' })
        continue
      }
      if (!descriptor.editable) {
        rejectedFields.push({ key: field.key, reason: '字段不可编辑' })
        continue
      }

      const normalized = this.normalizeValue(field, descriptor.dataType)
      if (!normalized.ok) {
        rejectedFields.push({ key: field.key, reason: normalized.reason })
        continue
      }

      // 这是 iGIX Angular 表单的正式字段赋值入口。
      this.frameContext.bindingData.setValue(descriptor.path, normalized.value, true, true)
      appliedFields.push(field.key)
    }

    this.postToPortal({
      type: 'IGIX_AI_PREFILL_ACK',
      version: '1.0',
      requestId,
      formKey: this.formKey,
      status: appliedFields.length === fields.length
        ? 'applied'
        : appliedFields.length > 0
          ? 'partial'
          : 'rejected',
      appliedFields,
      rejectedFields
    })
  }

  private normalizeValue(field: PrefillField, dataType: string):
    | { ok: true; value: unknown }
    | { ok: false; reason: string } {
    if (field.valueType === 'text' && dataType === 'String') {
      return { ok: true, value: String(field.value ?? '') }
    }

    if (field.valueType === 'number' && ['Integer', 'BigDecimal'].includes(dataType)) {
      const value = Number(field.value)
      return Number.isFinite(value)
        ? { ok: true, value }
        : { ok: false, reason: '不是有效数字' }
    }

    // 日期、枚举、人员、组织和关联字段必须依据运行时元数据转换，
    // 不能把显示名称直接写入关联控件。
    return { ok: false, reason: `暂不支持 ${dataType} 字段的输入格式` }
  }

  private readCurrentFormKey(): string {
    // 这里接入当前版本实际暴露的 form metadata/context API。
    return ''
  }

  private readCurrentFieldSchema(): Map<string, { path: string[]; dataType: string; editable: boolean }> {
    // 这里接入当前版本实际暴露的字段 schema；没有 schema 时必须安全失败。
    return new Map()
  }

  private postToPortal(message: Record<string, unknown>): void {
    const origin = (window as any).__IGIX_PORTAL_ORIGIN__
    if (!origin || window.parent === window) return
    window.parent.postMessage(message, origin)
  }
}
```

实际项目中，接收 `IGIX_AI_PREFILL_APPLY` 的监听器可以放在该控制器对应的组件中，也可以放在一个独立桥接组件中。关键要求不变：最终必须由当前表单的 `FrameContext` 或 `BindingData` 写值。

如果字段属于子表或组合表单，要先用 `frameContextManager.getFrameContextById(...)` 找到对应的 frame，再对该 frame 的 `bindingData` 操作：

```ts
const childFrame = this.frameContext.appContext
  .frameContextManager
  .getFrameContextById('实际子表或组合表单frameId')

childFrame.bindingData.setValue(
  ['子表编号s', 'deliveryDate'],
  value,
  true,
  true
)
```

`frameId` 必须从当前表单的实际运行时结构确认，不能沿用别的应用的示例值。

### 5.3 值类型处理规则

第一版先支持已经确认的简单字段：

- 普通文本；
- 普通数字；
- 已确认格式的日期。

以下类型必须根据当前表单元数据取得真实值格式后再开放：

- 人员；
- 组织；
- 关联对象；
- 枚举；
- 附件；
- 子表明细；
- 公式字段和只读字段。

例如人员字段通常需要平台识别的 ID、编码、名称或关联对象，而不是只写一个姓名。枚举字段需要真实枚举值，日期字段需要该控件接受的日期对象或格式。填错值类型会造成显示正确但保存失败，这是不能接受的假成功。

## 六、环宝助手和门户项目的代码改造

### 6.1 动态目录和可选兼容配置

不要新增一个要求维护所有表单的静态注册表。建议拆成两个能力：

1. `igixFunctionCatalog`：从当前门户运行时上下文或平台函数目录取得用户可访问菜单；
2. `igixFormMetadata`：从当前表单桥接器取得表单身份、字段 `code`、字段路径、数据类型和可编辑状态。

如果某个表单或平台版本确实缺少通用元数据入口，再增加一个**可选兼容配置**，只记录业务别名和特殊值转换，不记录全量菜单。

建议文件名：

```text
src/services/igixFunctionCatalog.js
src/services/igixFormMetadata.js
src/config/formBridgeOverrides.js
```

可选覆盖配置示例：

```js
export const formBridgeOverrides = {
  leave_request: {
    aliases: {
      出差项目: 'projectName'
    },
    valueConverters: {
      leaveStartDate: 'date'
    },
    blockedFields: ['id', 'version']
  }
}
```

这里不再保存全量 `funcId` 和全量字段 `path`。用户提供的 `193545d8-29f9-4790-99f0-6c517aca3e4f / LeaveOpsList` 是列表菜单，不能直接当成表单字段写入目标。应从列表进入新增或编辑后，由当前运行时确认真实 `LeaveOps` 表单身份和字段元数据。

### 6.2 新增助手侧桥接服务

建议新增：

```text
src/services/igixPrefillBridge.js
```

服务负责：

- 生成 `requestId`；
- 过滤和类型校验字段；
- 发送 `IGIX_AI_PREFILL_REQUEST`；
- 监听和匹配 ACK；
- 处理 60 秒超时；
- 将 ACK 转成 `applied`、`partial`、`rejected`、`timeout` 状态。

助手界面只在用户确认后调用该服务。预览阶段不能写入表单。

### 6.3 门户父页面适配器

门户监听器必须：

1. 校验 `event.origin` 是已配置的助手 origin；
2. 校验 `event.source` 是登记的助手 iframe；
3. 从当前用户函数目录解析并校验目标 `funcId`；
4. 丢弃模型生成的任意 `funcId` 和任意字段路径；
5. 保存 pending 请求并设置过期时间；
6. 调用 `gspframeworkService.rtf.func.openMenu`；
7. 等待目标表单 ready 和字段描述后再发送 apply；
8. 只接受目标表单 iframe 的 ACK；
9. 按 `requestId` 回传给助手并删除 pending。

所有 `postMessage` 都必须使用明确的 `targetOrigin`。不能再使用 `'*'`。

### 6.4 失败和降级

以下情况都必须降级，不得伪造成功：

- 不在 iGIX 门户环境；
- 找不到门户父页面；
- 当前表单没有可用字段元数据；
- 字段不在当前运行时元数据或审核过的覆盖范围；
- 表单桥接组件没有发布；
- 目标表单没有发送 ready；
- 目标表单返回 rejected；
- ACK 超时；
- 用户刷新或关闭了表单。

降级文案建议：

```text
表单已打开，但当前表单还没有启用智能回填桥接，请检查后手工填写。
```

## 七、请假表单 POC 执行步骤

### 7.1 目标选择

先不要从 `LeaveOpsList` 列表页做字段写入。列表页只负责展示和进入业务单据，字段回填目标必须是实际的 `LeaveOps` 表单页。

确认路径：

1. 用用户提供的 `193545d8-29f9-4790-99f0-6c517aca3e4f / LeaveOpsList` 打开请假台账；
2. 点击新增或打开一条记录；
3. 确认新打开的真实表单页面和表单编号；
4. 查看运行时 `frameContextManager.frameContextMap`，记录根表单 frame ID；
5. 从表单运行时或平台元数据确认字段 `code`、数据类型、可编辑状态和真实绑定路径；
6. 让通用桥接器读取这份字段描述，不把它抄成项目级全量注册表；
7. 如有业务歧义，只增加一个小型别名或值转换覆盖；
8. 先只开放一个字段做回填 POC。

### 7.2 最小可行字段

第一轮只做一个普通文本字段，例如已经确认是普通输入控件的项目字段。成功标准是：

- 用户在环宝助手中输入内容；
- 助手出现预览；
- 用户点击确认；
- iGIX 打开真实请假表单；
- 表单桥接器 ready；
- 目标文本框可见值变化；
- `BindingData` 发生变化，表单进入正确的脏值或变更状态；
- 助手收到 `applied` ACK；
- 页面没有自动保存或提交。

第二轮再增加日期和数字。人员、组织、枚举、子表另行做值类型适配。

### 7.3 运行时检查点

在浏览器开发者工具中依次检查：

1. 助手是否发送了 `IGIX_AI_PREFILL_REQUEST`；
2. 门户是否按白名单调用 `openMenu`；
3. 目标表单是否发送 `IGIX_AI_PREFILL_READY`；
4. 门户是否只向目标表单发送 `IGIX_AI_PREFILL_APPLY`；
5. 目标表单是否调用 `bindingData.setValue`；
6. 目标表单是否返回 `IGIX_AI_PREFILL_ACK`；
7. 助手是否根据 ACK 更新状态；
8. 未点击确认前是否完全没有 apply 消息；
9. 是否没有调用保存、提交、通过或驳回接口。

## 八、安全和数据边界

- 字段必须经过用户确认后才进入 apply 阶段；
- 只允许当前运行时字段描述中的字段 `code`，以及经过审核的少量别名和覆盖规则；
- `requestId` 必须唯一，并设置过期时间；
- 父页面校验助手来源，表单校验父页面来源；
- ACK 必须匹配当前 requestId，过期 ACK 丢弃；
- 不把完整字段长期写入 URL、localStorage 或日志；
- 当前用户信息只使用已经确认的白名单字段；
- 不允许自动保存、自动提交、自动审批；
- 不修改浪潮 `/platform/runtime/...` 原生部署包；
- 不复制原生压缩代码、图片和商用样式。

## 九、最终验收标准

### 必须通过

- `npm run build` 成功；
- 助手可以生成字段预览；
- 用户确认前没有打开表单和字段写入动作；
- 至少一个真实 iGIX Angular 表单完成字段回填；
- 回填通过 `BindingData.setValue` 完成；
- 页面可见值正确变化；
- 表单返回 `applied` ACK；
- 助手收到 ACK 后才显示已回填；
- 用户仍需自行检查并提交；
- 任务查询和原有问答功能不回归。

### 不能接受

- 只把字段显示在助手卡片里；
- 只调用 `fillform.updateData`；
- 只打开表单但没有写入；
- 只改 DOM 的 `input.value`；
- 没有 ACK 就显示成功；
- 把 `LeaveOpsList` 列表页当成字段写入目标；
- 把任意模型字段路径直接传给 `BindingData`；
- 修改服务器原生 `fillformwidget.js` 以伪造能力。

## 十、交付物

本次落实应至少形成以下内容：

```text
环宝项目：
  src/services/igixFunctionCatalog.js
  src/services/igixFormMetadata.js
  src/config/formBridgeOverrides.js（可选）
  src/services/igixPrefillBridge.js
  现有动作协议和助手 UI 的必要修改

iGIX 表单侧：
  IgixPrefillBridge 自定义业务组件或等价表单控制器
  leave_request 测试表单的字段元数据读取和安全校验
  已发布的测试表单版本

验证材料：
  构建结果
  浏览器操作步骤
  ready/apply/ack 日志
  真实表单回填截图
  未支持字段和降级说明
```

最重要的一句话：原生配置通过平台元数据知道表单有哪些字段，`fillform` 负责展示，通用表单桥接器负责写入，`BindingData.setValue` 才是这条链路真正落到业务表单里的最后一公里。
