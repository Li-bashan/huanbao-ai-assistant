### 3.1 `fillform` 的真实行为

部署文件：

```text
/platform/runtime/common/web/fillform/fillformwidget.js
```

公开全局对象：

```js
window.FillformWidget
```

公开 API：

```js
await window.FillformWidget.initialize()
await window.FillformWidget.cleanup()
const widget = window.FillformWidget.createWidget()

widget.updateOptions(options)
widget.updateData(data)
await widget.mount(domElement)
await widget.unmount()
await widget.dispose()
```

默认状态类似：

```js
{
  options: {
    mode: 'full',
    messageId: '',
    conversationId: '',
    implOptions: { id: '' }
  },
  data: {}
}
```

当 `data.resultType === 'fill'` 时，原生部件显示字段详情。核心数据形态为：

```js
{
  resultType: 'fill',
  fields: [
    { name: '项目名称', value: '污水处理改造' },
    { name: '联系人', value: '刘昊澎' },
    { name: '联系电话', value: '***********' },
    { name: '预算金额', value: '50000' }
  ],
  pcMenuId: '菜单标识',
  dataId: '业务数据标识',
  sessionId: '会话标识'
}
```

原生部件的视觉效果是：

- 标题为制单详情；
- 逐行展示字段名和值；
- 没有值时展示未填写；
- 底部提供打开菜单按钮。

打开菜单的实际行为为：

```js
window.top.gspframeworkService.rtf.func.openMenu({
  funcId: data.pcMenuId,
  tabId: data.dataId,
  entityParams: {
    id: data.dataId,
    action: 'LoadAndEdit1',
    union_session: {
      sessionId: data.sessionId
    }
  }
})
```

重要结论：`fillform` 这个前端包自身没有读取表单、调用大模型、生成字段或写入表单的逻辑。它主要负责展示外部传入的 `data`，然后打开已经准备好的业务数据。

### 3.1.1 必须新增表单侧桥接

本任务不能停留在 `fillform` 的字段预览。服务器上的原生包没有字段赋值 API，真正的字段回填必须由目标业务表单内的自定义业务组件或表单自定义控制器完成。

手册已经确认 iGIX Farris-Angular 表单的正式字段赋值方式：

```ts
this.frameContext.bindingData.setValue(
  ['字段编号'],
  value,
  true,
  true
)
```

因此，必须实现以下三方链路：

```text
环宝助手
→ IGIX_AI_PREFILL_REQUEST
→ 门户父页面校验、openMenu、保存 pending 请求
→ 真实表单桥接器 ready
→ IGIX_AI_PREFILL_APPLY
→ frameContext.bindingData.setValue
→ IGIX_AI_PREFILL_ACK
→ 环宝助手根据 ACK 显示真实状态
```

详细协议、Angular 控制器骨架、字段类型限制、请假表单 POC 和验收步骤见：

```text
docs/智能填单表单桥接实施说明.md
```

不得采用以下伪实现：

- 只调用 `FillformWidget.updateData`；
- 只把字段显示在助手卡片；
- 只打开表单后宣称已经填写；
- 直接修改目标页面 DOM 的 `input.value`；
- 没有表单 ACK 就显示成功。

当 `data.resultType === 'ask'` 时，原生部件显示追问文本和建议按钮：

```js
{
  resultType: 'ask',
  content: '请补充项目预算',
  suggestions: [
    '预算为50000元',
    { text: '预算暂不确定' }
  ]
}
```

原生建议按钮点击后会调用：

```js
window.top.AssistantIntgSDK.sendCommandViaCUI({
  message: {
    text: '预算为50000元',
    files: []
  },
  contextValues: {
    framework: {},
    user: {},
    capture: {}
  },
  assistantId: undefined,
  target: ''
})
```

本项目不要依赖这个原生 SDK。建议把建议按钮点击后的文本重新送回环宝自己的对话入口。

### 4.1 环宝智能填单

用户输入：

```text
帮我发起采购请示单，项目名称是污水处理改造，联系人用我自己，预算五万元
```

环宝助手应当完成：

1. 识别目标表单；
2. 读取当前登录用户白名单信息；
3. 使用规则解析或 Dify 解析字段；
4. 展示字段预览；
5. 标记缺失字段和低置信度字段；
6. 等待用户点击确认；
7. 确认后打开浪潮表单；
8. 等待真实表单桥接器 ready；
9. 将经过白名单校验的字段发送给真实表单；
10. 根据表单 ACK 显示已回填、部分回填或待人工填写；
11. 明确告知用户仍需检查后自行提交。

确认后必须尝试真实表单桥接。只有目标表单返回 `IGIX_AI_PREFILL_ACK` 且状态为 `applied` 或 `partial`，才能显示对应回填状态。表单未接入桥接、ready 超时或返回 `rejected` 时，必须显示已打开、部分回填或待人工填写。

## 六、模型输出协议

不要让大模型直接生成 HTML、JavaScript、菜单 ID 或任意平台参数。让模型只输出结构化 JSON。

建议模型输出：

```json
{
  "intent": "fill_form",
  "formKey": "purchase_request",
  "fields": [
    {
      "key": "projectName",
      "value": "污水处理改造",
      "source": "user",
      "confidence": 0.98
    },
    {
      "key": "contact",
      "value": "CURRENT_USER",
      "source": "user_default",
      "confidence": 0.95
    },
    {
      "key": "budgetAmount",
      "value": "50000",
      "source": "user",
      "confidence": 0.98
    }
  ],
  "missingFields": [],
  "clarification": ""
}
```

应用层必须做二次处理：

1. `formKey` 必须存在于 `formFieldRegistry.js`；

4. 金额、日期、枚举、组织等类型必须经过类型校验；
5. 不认识的字段直接丢弃并记录开发日志；
6. 缺失必填字段时进入澄清状态，不允许直接打开后宣称填单完成；
7. 确认前不发送写入动作。

## 七、门户父页面动作协议

现有 `src/utils/actionBridge.js` 使用了 `'*'` 目标 origin。实现本任务时必须改为明确的门户 origin 配置：

```js
const portalOrigin = import.meta.env.VITE_IGIX_PORTAL_ORIGIN

window.parent.postMessage(
  {
    type: 'IGIX_AI_ACTION',
    payload: actionPayload
  },
  portalOrigin
)
```

父页面需要校验：

- `event.origin` 是否是环宝助手地址；
- `event.source` 是否是预期 iframe；
- `payload.action` 是否在白名单；
- `formKey` 是否存在；
- `funcId` 是否与平台菜单映射一致；
- 字段是否在表单字段白名单内；
- `actionId` 是否已消费，避免重复执行。

建议动作：

```js
{
  action: 'open_menu',
  formKey: 'purchase_request_list',
  funcId: '菜单标识',
  actionId: 'uuid'
}
```

```js
{
  action: 'open_form',
  formKey: 'purchase_request',
  funcId: '9744034a-7fcc-4510-97fa-f563aecd26e6',
  fields: [
    {
      key: 'projectName',
      label: '项目名称',
      value: '污水处理改造'
    }
  ],
  actionId: 'uuid'
}
```

父页面必须实现真正的表单桥接转发：

1. 校验动作；
2. 打开表单；
3. 保存 `requestId`、`formKey`、字段白名单和过期时间；
4. 等待目标表单桥接器发送 ready；
5. 向目标表单发送 `IGIX_AI_PREFILL_APPLY`；
6. 接收并校验 `IGIX_AI_PREFILL_ACK`；
7. 将 ACK 转给环宝助手。

表单侧必须使用 `FrameContext` 或 `BindingData` 的正式接口写入字段。`query`、`session` 或 `entityParams` 只能携带请求标识和初始化参数，不能替代字段赋值。没有 ACK 不得返回伪造的已填充成功。

## 十、验收标准

只有满足以下条件才算完成：

- `npm run build` 成功；
- 制度问答、办公智能、智能问数原有功能不回归；
- 用户可以在环宝助手中查询自己的待办；
- 用户可以点击待办打开浪潮任务详情；
- 用户可以得到智能填单字段预览；
- 字段预览必须经过用户确认；
- 至少一个真实 iGIX Angular 表单可以通过表单桥接完成字段回填；
- 真实回填必须调用 `BindingData.setValue`，不能只修改 DOM；
- 表单必须返回 `IGIX_AI_PREFILL_ACK`，助手根据 ACK 展示状态；
- 菜单和字段均经过白名单；
- 没有调用浪潮智能体中心；
- 没有依赖 `cbf 多渠道对话框架`；
- 没有复制浪潮原生压缩包；
- 没有自动通过、驳回或提交；
- 没有使用 `postMessage(..., '*')`；
- 如果真实字段回填尚未打通，任务不得标记完成；在运行过程中界面必须诚实显示打开表单或待人工填写，而不是显示成功填单。

## 十二、最重要的产品判断

本任务不是把浪潮 `fillform` 原封不动搬过来，而是复现它对用户有价值的交互：

```text
自然语言
→ 结构化字段
→ 字段预览
→ 用户确认
→ 打开 iGIX 表单
→ 表单桥接器调用 BindingData.setValue
→ ACK 回传
→ 用户检查并提交
```

本任务也不是复制浪潮 `taskSearch` 的所有功能，而是复现它的只读主流程：

```text
当前用户
→ 查询待办
→ 展示任务卡片
→ 打开任务详情
```

用自己的大模型补上浪潮授权组件缺失的智能部分，用 iGIX 已经可用的平台服务完成页面跳转。这就是本项目在无 `cbf` 授权条件下的正式实现路线。
