更新时间：2026-09-15

状态：架构提案，尚未开始施工

## 0. 给后续 Agent 的阅读规则

本方案是下一阶段重构的唯一建设方向。任何 Agent 开始编码前，必须依次阅读：

1. 根目录 `AGENTS.md`

4. `docs/技术架构说明.md`

事实优先级：生产实测结果 > 当前代码和测试 > 当前现状文档 > 本方案中的目标设计。

仓库不再保存历史 Dify 报告、旧截图或旧 DSL。迁移时如需核对外部 Dify 资产，必须以目标环境的只读核验结果为准。

## 1. 架构决策

### 1.1 核心决策

生产环境移除 Dify 依赖。保留大模型能力，但由自有模型适配层、知识服务、问数服务和办公服务承接。

### 1.2 不变的原则

- 大模型只负责语言理解、改写和解释，不能成为业务事实的最终决定者。
- 指标定义、单位、公式、时间语义、组织范围和权限必须由服务端确定。
- 智能问数只能由一个后端计算引擎负责，前端不得重新求和、换单位或推导排名。
- 知识库检索必须独立、可版本化、可授权、可引用和可回溯。
- Gateway 是浏览器唯一入口，模型、知识库、数据库和业务服务不得被浏览器直连。

### 1.3 Dify 的最终位置

Dify 不进入生产主链路。迁移完成后可保留为隔离的实验工具，但不能被生产请求依赖，不能持有生产数据库凭据，不能决定生产指标和权限。

## 2. 当前系统基线

截至 2026-09-15，当前仓库已经具备：

- Vue 3 + Vite 的 iGIX 门户右侧助手前端。
- Spring Boot AI Gateway，负责身份、问数权限、SSE 代理、会话和部分审计。
- 独立 `huanbao-dataquery` 服务，负责意图识别、数据查询、指标计算、结构化结果和 SSE。
- 制度、办公、Master 的 Dify 代理配置和兼容代码仍存在。
- 流程助手使用前端规则和 `IGIX_AI_ACTION`，不调用 Dify。
- 问数当前 Gateway 代码链路已经是 Gateway -> `huanbao-dataquery:8089`，不再需要 Dify 执行问数；旧 Dify 配置和历史文档仍需清理。
- 最新问数修复提交为 `3dd2a71`，已推送 `origin/main`，`huanbao-dataquery` 生产服务已重启并返回 `UP`。
- 2025 年生活垃圾入厂量生产实测为 `2165.683098 万吨`，包含实际授权的 63 家组织；旧的 `139,521,585.36 万吨` 是单位漏换算和累计值重复求和共同造成的错误。
- 图二参考数 `2181.85 万吨` 与当前问数数据源仍存在 `16.166902 万吨` 差异，数据源、组织范围或快照尚未完成对账。

### 当前已知页面故障模式

- 前端固定兜底文案“暂未获取到该维度的结构化分析数据”实际表示没有收到通过校验的 `protocolVersion=2.0` 结构化结果，不应被当作“数据库没有该维度数据”。
- 推荐问题点击后和手工输入共用 `sendMessage` 及同一 Gateway/问数服务链路；多条推荐题目同时失败时，应先检查共享链路、语义字典、权限和协议，不要只改推荐按钮。
- dataquery 当前将未知指标返回为 `QUERY_NOT_SUPPORTED`，其他执行异常返回 `QUERY_EXECUTION_FAILED`；后续必须保留 requestId、失败阶段和可行动错误原因，禁止只向用户展示通用“执行失败”。
- 这三类故障都要纳入 golden case 和前端契约测试，验收必须覆盖推荐问题、手工问题、结构化结果和异常状态。

## 3. 建设目标与边界

### 3.1 In scope

- 统一模型适配和流式输出。
- 独立制度知识库、检索、引用和权限。
- 指标语义中心、组织权限中心和确定性问数引擎。
- 办公提示词模板、版本管理和模型调用服务。
- 统一结果协议 v3。
- 前端纯展示化，删除旧协议业务计算。
- Dify 资产迁移、双跑、切流、下线和密钥回收。
- 数据血缘、质量校验、对账、审计、监控和回滚。

### 3.2 Out of scope

- 不替换现有 ERP、生产业务系统和 KingbaseES 原始数据系统。
- 不在第一阶段开放自动审批、自动提交或无 ACK 的门户动作。
- 不把历史 Dify 的 SQL 结果直接复制为新系统事实。
- 不通过页面硬编码修正业务数字。

## 4. 目标架构

```text
iGIX 门户
  ↓ 签名身份 / iframe 协议
AI Gateway
  ├─ 身份认证、DataScope、限流、审计、统一错误
  ├─ Model Adapter：统一模型接口和流式响应
  ├─ Knowledge Service：文档、索引、检索、引用、权限
  ├─ Data Query Service：计划、语义、SQL、计算、校验
  ├─ Office Service：模板、上下文、写作和导出
  └─ Workflow Service：动作校验、门户 ACK、业务 API
          ↓
  KingbaseES / MinIO / OpenSearch / 业务系统
```

## 5. 核心服务设计

### 5.1 AI Gateway

保留现有 Gateway 作为唯一对外入口，新增或统一以下能力：

- `X-Portal-Identity` 签名身份校验。
- 用户、租户、组织和指标权限解析。
- 服务间 mTLS 或等价的内部认证。
- 请求 ID、会话 ID、模型版本、提示词版本和数据快照 ID 的统一传递。
- SSE 心跳、超时、取消、限流和错误映射。
- 不记录 API Key、数据库密码、完整敏感 Prompt 和敏感文档正文。

### 5.2 Model Adapter

统一封装本地 vLLM/Qwen 和其他 OpenAI-compatible 模型，提供：

- `chat` 和结构化 JSON 输出。
- 流式 token 输出。
- 模型、温度、最大 token、超时和重试策略的服务端配置。
- Prompt 模板版本绑定。
- 调用耗时、Token 和失败阶段审计。

模型适配层可以替换供应商，但上层服务不能依赖某个模型的私有返回格式。

### 5.3 Knowledge Service

独立管理：

- 原始文件和文档版本。
- 文档解析、OCR、清洗、切片和索引。
- 关键词检索、向量检索、混合召回和重排。
- 租户、组织、密级和角色权限。
- 引用文档、章节、页码、版本和生效时间。

建议使用 MinIO 保存原文件，OpenSearch 做混合检索，KingbaseES 保存元数据和权限。Dify 知识库资产必须先导出原文、元数据、权限和引用关系，再重新解析和建索引，不能只迁移向量。

### 5.4 Data Query Service

现有 `huanbao-dataquery` 作为基础继续演进，但必须明确为唯一问数权威：

```text
自然语言
  ↓
QueryPlan
  ↓
指标、时间、组织、权限、聚合校验
  ↓
受控 DSL / 确定性 SQL 编译
  ↓
原始数据查询
  ↓
单位、公式和时间语义计算
  ↓
结果质量与业务报表对账
  ↓
Result v3
```

大模型可以作为 QueryPlan 解析器，但必须返回结构化计划；计划必须经过后端校验，模型不能直接生成可执行 SQL。

### 5.5 Office Service

办公写作由提示词模板和模型服务完成，模板必须版本化：

- 会议纪要
- 通知公告
- 总结汇报
- 经营分析材料
- 邮件和润色

办公服务可以接入 Knowledge Service 提供制度或业务上下文，但输出必须标记引用来源和生成版本。复合问数材料必须只使用问数服务给出的事实快照。

### 5.6 Workflow Service

流程助手保持动作卡片和门户协议边界：

- 服务端校验动作、入口、参数和权限。
- 父页面 ACK 前不显示业务成功。
- `actionId` 服务端幂等。
- 动作尝试、成功、失败和超时全部进入审计。
- 智能填单必须等真实字段元数据和父页面 ACK 闭环后再开放。

## 6. 统一语义模型

### 6.1 指标定义必须包含

```text
metricCode
formalName
aliases
rawUnit
displayUnit
valueType: FLOW / STOCK / RATIO / COUNT
timeSemantics: PERIOD_INCREMENT / YTD / PERIOD_END / AVERAGE
aggregationRule
formulaAst
sourceTables
dimensionGrain
version
effectiveFrom / effectiveTo
```

### 6.2 查询计划必须包含

```text
metricCode
organizationScope
timeRange
granularity
requestedMeasure: PERIOD_VALUE / ANNUAL_SUM / YTD / LATEST
analysisType
comparison
authorizationSnapshot
```

### 6.3 结果必须包含

```text
value
unit
valueSemantics
period
metricCode
formulaVersion
sourceTables
dataCutoffDate
organizationScope
qualityStatus
```

缺少单位、公式版本、来源或时间语义时，结果不得标记为可信成功。

## 7. API 方向

### 7.1 对外 Gateway API

| API | 用途 | 返回 |
|---|---|---|
| `POST /api/ai/data-query/chat` | 智能问数 | SSE，阶段、v3 结果、错误、完成 |
| `POST /api/ai/knowledge/chat` | 制度问答 | SSE，答案、引用、版本、错误 |
| `POST /api/ai/office/chat` | 办公写作 | SSE，文本增量、模板版本、完成 |
| `POST /api/ai/workflow/actions/validate` | 动作预校验 | JSON，动作是否合法和原因 |
| `POST /api/ai/action-audits` | 动作审计 | JSON，服务端写入审计 |

### 7.2 问数结果协议 v3 最低要求

- `status` 必须区分成功、有数据、无数据、权限拒绝、语义歧义、校验失败、执行失败和对账失败。
- `content` 只承载展示数据，不允许前端自行推导业务字段。
- `dataInfo` 必须包含指标、单位、时间语义、组织范围、源表、截止日期和质量状态。
- `trace` 必须包含 requestId、planVersion、formulaVersion、snapshotId 和服务版本。
- SSE 必须有 `stage`、`analysis_result`、`error`、`completed`，客户端断开必须取消上游任务。

## 8. Wave 建设计划

### Wave 0：现状冻结与规格基线

- 盘点全部 Dify 应用、知识库、提示词、模型、数据连接、发布版本和生产密钥引用。
- 建立问数、制度、办公、流程的 golden case 和预期结果。
- 冻结 v3 语义、API、错误码、审计和数据血缘规范。
- 明确图二 `2181.85` 的权威来源，并完成当前 `2165.683098` 的差异对账。

验收：资产清单、数据口径清单、OpenAPI/JSON Schema、golden case 全部进入版本库；没有删除任何 Dify 资产。

安全：清单脱敏，不记录 Key、密码、完整签名和敏感文档正文。

### Wave 1：统一模型服务和 Gateway 收口

- 新增 Model Adapter 和 Prompt Registry。
- 将办公、制度和问数统一为 Gateway 内部服务调用。
- 统一 SSE、超时、取消、重试、错误码和审计字段。
- 生产禁止浏览器直连模型和 Dify。

验收：模型替换不影响业务 API；断开客户端能取消上游；同一 Prompt 版本可回溯。

安全：模型服务只能接受 Gateway 服务身份，拒绝浏览器伪造的权限字段。

### Wave 2：独立知识库

- 迁移 Dify 原文和元数据。
- 建设解析、切片、索引、混合检索、重排和引用服务。
- 实现组织、角色、密级和生效时间过滤。
- 建立文档发布、回滚和索引重建流程。

验收：制度问题回答引用可定位到文档、章节和版本；权限变更即时生效；索引失败不会发布半成品。

安全：检索前做 ACL 过滤，不能先召回后隐藏；原文和向量按租户隔离。

### Wave 3：问数语义和计算内核

- 将指标字典、公式、单位、时间语义、组织映射和数据源统一入库。
- 将 QueryPlan 校验和 SQL 编译收口到 `huanbao-dataquery`。
- 删除指标编码特例和前端业务计算。
- 增加质量校验、血缘和业务报表对账。

验收：吨到万吨只换算一次；月度发生量、年度总量、YTD、期末值不可混淆；所有结果可追溯到源表和公式版本。

安全：数据库账号只读；SQL 只能由受控计划编译；组织和指标权限在查询执行边界强制生效。

### Wave 4：制度、办公和流程迁移

- 制度从 Dify 知识检索迁移到 Knowledge Service。
- 办公从 Dify Agent 迁移到 Office Service。
- 流程接入 Gateway 校验、门户 ACK 和服务端幂等审计。
- 复合问数材料只消费问数结果快照。

验收：旧 Dify 与新服务双跑结果可比较；办公输出保持流式；制度引用和流程 ACK 不退化。

安全：制度和办公上下文不能越权混用；流程动作必须经过服务端权限和幂等校验。

### Wave 5：前端协议收口

- 前端切换 v3 结果协议。
- 删除 `DataQueryResult.vue` 的 legacy 业务计算和文本猜测。
- 前端只渲染后端的 value、unit、semantics、chart 和 evidence。
- 错误状态按机器码展示可行动提示，不再把所有问题归为一句 fallback。

验收：前端不执行指标求和、单位换算、同比环比或排名；页面和导出内容与后端结果逐字段一致。

安全：Markdown/HTML 继续消毒；不把服务端 SQL、Key、内部路径和敏感文档返回浏览器。

### Wave 6：双跑切换和 Dify 下线

- 先切换非关键测试用户，再切换生产流量。
- 记录新旧结果差异、延迟、错误率和引用命中率。
- Gateway 关闭 Dify 生产路由和配置读取。
- 回收 Dify 数据库凭据、API Key、网络访问和运维权限。
- 保留脱敏备份和回滚窗口，确认无生产依赖后再归档 Dify。

验收：生产请求中 Dify 调用数为 0；问数、制度、办公和流程全部通过 golden case；回滚演练成功。

安全：下线前先撤销凭据，再关闭网络；不得先删除数据再补迁移。

## 9. 自动化验收标准

### 数据正确性

- 如果 Wave 0 业务对账确认图二口径，原始 `21,818,500 吨` 应在该指定口径下转换为 `2,181.85 万吨`；在确认前它只是待核验 golden case，不是当前系统事实。
- 月度发生量之和等于年度总量。
- YTD 序列不能再次被前端求和。
- 单位、公式版本和数据截止日期每次都返回。
- 组织范围和排名数量不超过授权集合。
- 业务报表差异超过阈值时阻断可信成功并给出对账状态。

### 体验与协议

- 推荐问题和手工问题走同一解析、执行和协议链路。
- 所有阶段都有明确状态，不能出现无限处理中或空白成功。
- SSE 断开可取消，超时可重试，重试不重复写入审计。
- 前端、CSV、Word 和图表使用同一份后端结果。

### 安全与运维

- 未签名身份、越权组织、越权指标、非法计划全部拒绝。
- 生产日志不出现密码、Key、签名原文、完整文档和 SQL 敏感参数。
- 记录 requestId、userId 脱敏值、组织范围摘要、服务版本、数据快照和结果状态。
- 监控成功率、P95、超时率、模型错误率、检索命中率、对账差异率和数据截止日期滞后。

## 10. 发布和回滚

- 所有代码通过 GitLab CI 测试、构建、备份、部署和健康检查。
- 新服务采用独立版本号和配置校验，禁止缺配置时静默降级到 Dify。
- 数据库新增表和索引必须有只读前置检查、备份、迁移记录和回滚脚本。
- 切流使用 Gateway feature flag，支持按用户、租户和能力灰度。
- 回滚只回滚路由和服务版本，不回滚或覆盖原始业务数据。

## 11. 后续 Agent 的施工纪律

- 先更新 Spec 和本方案对应的状态，再编码。
- 每个 Wave 先做最小端到端垂直切片，再扩展其他指标和场景。
- 不允许为了通过页面截图硬编码业务数字。
- 不允许把 Dify 旧 Prompt、旧 SQL 或旧协议直接复制为新系统的权威实现。
- 每个改动必须有单元、集成、契约和必要的真实数据验证。
- 未完成双跑、回滚和生产无 Dify 依赖验证前，不得删除 Dify 资产。
