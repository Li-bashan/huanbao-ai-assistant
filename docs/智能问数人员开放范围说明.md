# 智能问数人员开放范围说明

更新时间：2026-08-28

## 当前实现

当前智能问数只开放生产指标数据查询，采用试点阶段的前端静态人员白名单控制：

```text
iGIX 当前登录人 name
        ↓
src/config/dataQueryAccess.js
        ↓
前端静态名单
        ↓
covered=true 允许展示智能问数并发起查询
covered=false 展示暂未覆盖提示
```

当前 Dify 查询工作流的实际节点、发布状态和数据库链路见[《Dify 智能问数工作流现状》](./Dify智能问数工作流现状.md)。截至 2026-08-28，Dify 工作流直接使用 Kingbase SQL 插件，尚未通过 AI Gateway 做服务端用户鉴权；本文件下面的 Gateway 二次校验属于后续动态模式方案。

当前用户由已有 `src/utils/igixUser.js` 读取。同源时直接调用：

```js
const userInfo = window.gspframeworkService.common.userInfos.get()
```

跨域 iframe 不能直接读取门户父页面对象，因此助手会发送 `IGIX_AI_USER_REQUEST`，由门户父页面读取自己的 `gspframeworkService.common.userInfos.get()` 后回传 `IGIX_AI_USER_RESPONSE`。用户信息桥接不固定助手 origin，父页面应校验 `event.source` 是当前助手 iframe，并将回执发回 `event.origin`，不能使用 `*`。具体父页面代码见 `docs/门户嵌入说明.md`。

iframe 环境会兼容 `window.parent`，并复用 `getIgixCurrentUser()`。现阶段实际匹配字段只有 `currentUser.name`；`userId`、组织和租户字段仍保留。

未覆盖用户看到的统一文案是：

> 您所在部门暂不支持生产指标智能问数，如有业务需要，请联系管理员申请。

## 前端名单维护

直接修改 `src/config/dataQueryAccess.js`：

```js
export const DATA_QUERY_ALLOWED_USER_NAMES = [
  '刘昊澎',
  '姚国旗',
  '仇亿伦',
  '李金钟',
  '王邯宝',
  '系统管理员',
]
```

修改后必须重新构建并重新发布前端：

```bash
npm run build
```

原来的数据库表、管理接口和管理页面仍保留，供后续切回动态名单时使用；当前静态名单模式不会请求 `/api/ai/data-query/access`，因此本地演示不依赖 PostgreSQL 或 AI Gateway。

管理页面入口仍是：

```text
/?page=data-query-users
```

当前静态名单模式不使用管理 CRUD。后端管理 CRUD 仍使用环境变量 `DATA_QUERY_ADMIN_TOKEN`，后续恢复动态名单时再启用。

## 后续动态模式的服务端二次校验

下面是切回数据库动态名单后的方案，当前前端静态名单模式不会调用这条开放范围接口。

前端请求智能问数 Dify 时，会在 `inputs` 增加：

```json
{
  "current_user_name": "张三"
}
```

Dify HTTP 节点必须将这个值放进 Gateway 请求体：

```json
{
  "userName": "{{ current_user_name }}",
  "queryCode": "...",
  "params": {}
}
```

Gateway 的 `DataQueryAccessService.requireCovered(userName)` 位于 `DifyDataQueryService.query()` 查询分发之前。缺少姓名返回 `CURRENT_USER_MISSING`，不在启用名单返回 `DATA_QUERY_NOT_COVERED`，都不会进入数据库查询分支。

静态名单模式下，前端名单和 `covered` 状态都可以被 DevTools 修改，因此只能用于领导演示或内部试点，不能阻止用户绕过页面直接调用 Dify。

## 试点定位与已知安全缺陷

当前实现定位是领导演示 / 试点开放范围控制，不是正式生产身份认证与数据权限体系。

```text
TODO:
当前智能问数试点阶段使用 iGIX 前端获取的 userInfo.name
进行人员白名单匹配。

该方案仅用于领导演示 / 试点开放范围控制，
不能等价为正式生产安全身份认证。

正式生产环境后续升级为：
1. 服务端从可信 iGIX / SSO 登录态识别当前用户；
2. 使用稳定 userId，而不是姓名；
3. AI Gateway 不再信任前端直接提交的 userName；
4. 再增加组织、角色、大区、项目公司、指标等数据范围权限。
```

当前必须接受的演示阶段风险：`current_user_name` 最终来自浏览器侧 iGIX 用户信息，懂前端或 HTTP 请求的人理论上可以篡改 `userName`，冒充另一个已在名单中的姓名。本次不使用前端混淆、隐藏参数或加密姓名来假装解决身份可信问题。

后续升级方向：

- 使用可信服务端 `userId` 和 SSO / iGIX 登录态。
- 增加组织、角色、`REGION`、`COMPANY` 数据范围。
- 增加指标级权限和完整审计。
- 让 Dify / Gateway 链路只信任服务端身份上下文。

## 运行配置

当前静态名单模式只需要构建前端。下面的 Gateway 配置仅在启用动态名单、人员管理或服务端二次校验时使用：

```text
DATA_QUERY_ADMIN_TOKEN=replace-with-a-long-random-secret
AI_GATEWAY_CORS_ALLOWED_ORIGINS=http://localhost:5173,https://portal.example.com
AI_GATEWAY_DB_URL=...
AI_GATEWAY_DB_USERNAME=...
AI_GATEWAY_DB_PASSWORD=...
```

静态名单新增、删除或修改后，需要重新执行 `npm run build` 并重新发布前端。动态数据库名单才使用管理页面实时生效。
