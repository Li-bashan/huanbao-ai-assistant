# 文档与目录规范

更新时间：2026-09-15

本文是本项目的文档治理规则。它解决的是文档应该放在哪里、谁可以把什么写成当前事实，以及什么时候必须删除，而不是业务功能设计。

## 1. 项目根目录应该放什么

根目录只放能直接影响构建、运行、协作或发布的文件：

```text
README.md              项目入口：是什么、怎么启动、怎么验证、去哪里查详细资料
AGENTS.md              Codex/Agent 工作约束
CLAUDE.md              其他 Agent 的兼容入口，内容不得与 AGENTS.md 分叉
CHANGELOG.md           精简的用户可感知变更
package.json           前端依赖和命令
vite.config.js         前端构建配置
.env.example           非敏感配置模板
.gitlab-ci.yml         自动测试、构建和发布流水线
src/                   前端源代码
public/                前端静态资源
ai-gateway/            Gateway 源代码
huanbao-dataquery/     独立问数服务源代码
tools/                 可重复执行的开发、验收和发布工具
docs/                  当前文档、契约、数据源和迁移脚本
```

`dist/`、`target/`、`node_modules/`、截图、临时报告、发布压缩包和本地日志都属于生成物，不进入版本库。

## 2. docs 目录的责任边界

```text
docs/
  README.md                         文档入口和阅读顺序
  项目现状总览.md                    当前事实、风险和优先级
  项目交接说明.md                    新 Agent 的最短接手路径
  技术架构说明.md                    当前链路与目标架构
  去Dify化智能助手整体建设方案.md    尚未施工的总体方案
  产品功能说明.md                    面向产品和验收人员的能力边界
  部署说明.md                        发布、回滚和环境变量
  验证清单.md                        可执行的测试与验收项
  数据源与指标基线.md                问数源表、指标口径和对账基线
  文档与目录规范.md                  本文
  reference/                         当前有效的接口、门户和流程契约
  sql/                               可执行或待执行的数据库 DDL/迁移脚本
  业务Excel/                          经确认的业务输入源文件
  METRIC_SEMANTIC_DICTIONARY.json    问数服务运行时加载的语义字典
```

根目录的几份当前文档是稳定入口，不能再增加 `*-交付报告`、`*-核对报告`、`*-抓取报告` 这种平行真相源。专项资料必须归入 `reference/`，并且标明 `current`、`proposed` 或 `host-pending` 状态。

## 3. 文档按用途写，不按日期堆

本项目采用 Diátaxis 的四种文档用途：

- 教程：带新 Agent 或新开发者完成一条完整路径。
- 操作指南：解决部署、排障、联调等具体任务。
- 参考：记录接口字段、协议、配置、SQL 和稳定映射。
- 解释：解释架构决策、边界和取舍。

当前映射如下：

| 用途 | 本项目文件 | 写作要求 |
|---|---|---|
| 教程 | `README.md`、`项目交接说明.md` | 只保留最短可执行路径 |
| 操作指南 | `部署说明.md`、`验证清单.md`、`reference/智能填单表单桥接实施说明.md` | 步骤、前置条件、失败处理必须可执行 |
| 参考 | `reference/`、`sql/`、语义字典、数据源基线 | 以契约和事实为准，不写猜测 |
| 解释 | `技术架构说明.md`、`去Dify化智能助手整体建设方案.md` | 说明为什么这样设计，并明确提案与已实现的区别 |

## 4. 当前事实和历史记录的规则

1. `项目现状总览.md` 是当前事实总入口，交接文档是当前接手入口。
2. 代码、测试、生产只读核验和业务源数据优先于旧文档。
3. 历史交付报告、旧截图、旧发布包和旧 Dify DSL 不作为当前证据；没有独立追溯价值就删除。
4. 需要保留的变更只写入 `CHANGELOG.md` 的摘要，不再新建一份报告。
5. 方案必须写清楚 `尚未施工`，不能把设计稿、提示词或枚举当作上线能力。
6. 数值、权限、数据截止日期和接口状态必须带来源；未知就写未知，不用历史数字填空。

## 5. 命名和维护规则

- 文件名表达内容，不使用“最终版”“最新版”“新”“备份2”等版本词。
- 同一主题只允许一个当前权威文件；其余文件必须是引用、脚本或源数据。
- Markdown 使用 UTF-8、相对链接和清晰的一级标题；不要嵌入绝对本机路径。
- API 参考未来应逐步迁移为 OpenAPI 文档或从 OpenAPI 生成；手写说明必须和实际 Controller/DTO 同步。
- 数据库脚本必须说明适用前置版本、是否幂等、是否已在目标环境执行；不把执行日志保存为项目文档。
- 截图只在缺少文字证据时保留单张验收样例，放在外部制品或任务附件，不提交整批布局截图。
