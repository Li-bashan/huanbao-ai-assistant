## 3. 当前代码链路

```text
iGIX 门户 iframe
  └─ Vue App.vue
      ├─ 制度问答 /api/ai/master/chat       ← 当前工作区未提交改动
      ├─ 办公智能 /api/ai/master/chat       ← 当前工作区未提交改动
      ├─ 智能问数 /api/ai/data-query/chat   ← Gateway 身份/授权/SSE
      └─ 流程助手 前端 Mock + postMessage   ← 不调用 Dify

AI Gateway
  ├─ MasterChatController → DifyMasterChatService
  ├─ PolicyChatController → Dify blocking 代理
  ├─ OfficeChatController → Dify streaming 代理
  └─ DataQueryChatController → 身份、授权、会话、限流、审计、Dify SSE
```

兼容路由 `/api/ai/policy/chat` 和 `/api/ai/office/chat` 仍在代码中，但当前工作区 `App.vue` 的制度/办公主路径通过 `sendMasterChatMessage` 走统一 Master 路由。工作区这些改动尚未提交、尚未证明已部署到生产，文档不把它写成线上事实。

## 5. Dify 资产和文档冲突

仓库内现有深度审计记录了控制台中四个以“智慧办公—”开头的应用，包含统一中枢、独立问数、办公助手、制度助手；同时历史文档仍大量使用 `01-数据库查询助手` 和 `200bb456...`。当前 Gateway 配置只保存 Base URL 和 Key，不保存 App ID，因此源码本身无法证明 Key 对应哪一个 App/发布版本。

目前可安全写入文档的说法是：

- Dify 控制台存在候选应用和历史工作流资产，部分控制台节点/版本信息见 `PROJECT_AUDIT_REPORT.md`。
- `DIFY_MASTER_API_KEY`、`DIFY_POLICY_API_KEY`、`DIFY_OFFICE_API_KEY`、`DIFY_DATA_QUERY_API_KEY` 的实际绑定关系需要在服务器环境用不泄露密钥的方式核对。
- 问数必须同时核对最终输出是否满足 `protocolVersion=2.0`，以及 Dify 是否真正消费 Gateway 下发的 `auth_context_json` / DataScope。
- Dify 能连到 Kingbase 插件或页面能打开，不等于本项目真实业务查询已经通过 Gateway 权限边界完成。

## 6. 权限、数据库和审计边界

当前 Gateway 默认使用签名身份模式：服务端校验 `timestamp + signedIdentity` 的 HMAC，要求得到 `userId` 和 `userName`；浏览器自行提交的 `userContext` 不能覆盖签名身份。问数开放范围由 `ai_data_query_user` 设计控制，问数审计由 `ai_data_query_audit` 设计承接。

但本次没有建立有效门户身份，没有连接 KingbaseES，没有执行仓库 DDL，也没有通过 Dify 间接查询业务数据。因此以下事项仍是待验收，而不是已完成：生产授权表是否存在并有数据、审计表是否存在、会话映射表是否建成、Dify SQL 是否执行组织过滤、指标/组织表真实字段和数据质量是否匹配。

流程动作审计接口已经存在，但 `sendIgixAction` 当前没有自动调用动作审计接口；动作发送成功只代表浏览器发出了 postMessage，不代表业务系统执行成功或审计已落库。
