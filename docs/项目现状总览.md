## 5. 当前代码链路

### 制度和办公

当前工作区的 `App.vue` 对制度问答、办公智能调用 `sendMasterChatMessage`，通过：

```text
前端 App.vue
  -> POST /api/ai/master/chat，SSE
  -> Gateway 服务端 Dify Master 配置
  -> Dify chat-messages streaming
```

`src/services/chatApi.js` 仍保留制度 blocking 和办公 streaming 的兼容分发；如果回退到已提交主线，应重新确认页面调用的实际函数和环境变量。

### 智能问数

```text
前端 dataQueryApi.js
  -> POST /api/ai/data-query/access
  -> POST /api/ai/data-query/chat，SSE
  -> Gateway 签名身份、服务端 DataScope、限流、opaque 会话映射和审计
  -> Dify /chat-messages
  -> Dify 当前实际绑定资产待确认
```

浏览器只持有环宝会话句柄，不应持有 Dify Key、Dify conversation ID、SQL 或数据库连接信息。

### 流程和门户

```text
用户输入
  -> intentRouter / workflowActions
  -> 已验证流程动作卡片
  -> actionBridge 清洗 payload、注入 actionId
  -> IGIX_AI_ACTION -> 门户父页面
```

当前父页面执行结果回执和 Gateway 动作审计尚未形成闭环。

## 6. 关键风险

- 代码已完成 git push；在服务器 pull、Nginx reload 和生产回归完成前，不能说生产已同步。
- Dify 文档中同时出现 `智慧办公—智能问数`、`01-数据库查询助手`、10/15、13/18、28/29、28/30 等不同资产/版本。本次没有足够登录态证据确认 Gateway 实际使用哪一个，必须先完成绑定核对。
- 目标 Dify 草稿被审计发现没有 `auth_*` / `allowed_org` 权限上下文引用，因此 Gateway 入口鉴权不能自动证明 SQL 已按用户数据范围过滤。
- 本次未建立 KingbaseES 直连，也未执行数据库 SQL；表结构、字段注释、样本数量和真实业务数据不能用 Prompt 或历史报告代替。
- `BODY_TRIAL` 默认关闭；没有门户签名身份时，独立浏览器不能使用问数。
- `IGIX_AI_ACTION` 已解析目标 Origin，但父页面仍需按 `actionId` 幂等消费；动作校验、回执和审计尚未由前端调用形成闭环。
- 问数异步 chunk 约 715 kB，当前只是性能告警，不阻断功能。

## 7. 当前验收重点

1. 在目标门户提供有效签名身份，验证制度、办公和智能问数的真实请求。
2. 确认 Gateway 的 Dify API Base/Key 实际绑定的 App、published workflow 和返回协议。
3. 在 Dify/Kingbase 环境核验权限上下文是否进入 SQL 执行边界；不能只看 Gateway 收到 `auth_*`。
4. 在真实 iGIX 环境验证窗口状态、用户握手、采购请示单动作幂等和执行回执。
5. 仅在本地构建、后端测试和目标环境回归都通过后，再 push、服务器 pull、重建和 reload。
