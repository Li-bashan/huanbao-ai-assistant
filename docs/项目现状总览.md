# 环宝 AI 助手项目现状总览

更新时间：2026-08-28

本文是项目当前状态的总入口，面向接手开发、联调、部署和验收人员。代码、服务器实际配置和 Dify 数据库核验结果优先于历史方案文档；方案、研究和待接入内容会明确标记为“计划”或“待验证”。

## 1. 一句话结论

项目已经是可演示、可使用的 Vue 3 + Vite 企业门户右侧助手 V1。制度问答、办公智能和智能问数都已接入 Dify，流程助手仍是前端动作卡片试点版。当前智能问数 Dify 工作流虽然能直接查询 KingbaseES，但仍未调用仓库内 AI Gateway，前端人员白名单也只是页面侧静态限制，不能当作生产级服务端授权。

Dify 实例一共核验到 10 个应用。应用、已发布工作流、最新草稿、测试和已删除历史记录的完整清单，以及其他工作流的节点情况，统一见[《Dify 全部应用与工作流现状》](./Dify全部应用与工作流现状.md)。

服务器容器、端口、模型供应商、已安装插件、持久化目录、备份和安全配置见[《Dify 服务器部署与模型配置》](./Dify服务器部署与模型配置.md)。

当前项目真正相关的 Dify 资产是：

- 制度问答：`智慧办公—环宝制度智能助手`，5 节点 / 4 连线，`公司制度`知识库。
- 办公智能：`智慧办公-环宝办公智能助手`，`agent` 应用，无 Workflow 图。
- 智能问数：`智慧办公—智能问数`，已发布版本 28 节点 / 30 连线；最新草稿同样 28 / 30，但尚未发布。

智能问数 28 个节点的输入、检索、SQL 生成、首轮执行、失败修复、补查、计算、图表和最终输出见[《Dify 智能问数工作流现状》](./Dify智能问数工作流现状.md)。

## 5. 当前真实链路

### 制度问答

```text
用户输入
  -> 前端 chatApi.js blocking
  -> Dify 制度问答应用
  -> 公司制度知识库检索
  -> LLM + think 清洗
  -> 引用来源和答案返回前端
```

### 办公智能

```text
用户输入
  -> 前端 chatApi.js Agent streaming
  -> Dify Agent 应用
  -> SSE 增量更新
  -> 前端过滤 <think> 后展示和保存
```

### 智能问数

```text
用户输入
  -> 前端静态人员名单检查
  -> 前端 chatApi.js streaming
  -> Dify 智能问数应用
  -> 指标字典 / 指标规则检索
  -> Qwen 生成 SQL
  -> SQL 解析校验
  -> rookie_text2data 插件直连 KingbaseES
  -> 失败修复、补查、计算、图表和回答
```

当前链路没有 Dify HTTP 节点，没有把 `current_user_name` 传入 Gateway，也没有服务端身份二次校验。AI Gateway 目前只用于前端人员管理 CRUD 等已接入接口，不能把它描述成当前查询链路的一部分。

## 6. 前端和 AI Gateway 边界

当前智能问数页面的开放范围由 `src/config/dataQueryAccess.js` 静态姓名名单控制，实际 Dify 工作流没有消费 `inputs.current_user_name`。仓库内 `ai-gateway/` 已实现健康检查、制度问答代理、智能问数 access 检查、查询前校验、人员 CRUD、动作校验和审计接口，但这些代码存在不等于前端和 Dify 已经切换完成。

当前主要风险：

- 前端直连 Dify，`VITE_*_DIFY_API_KEY` 会进入浏览器构建产物。
- 前端静态名单只能控制页面入口，不能证明真实用户身份和数据库访问权限。
- 智能问数首轮 SQL 节点端口当前存在常量 `54321`，补查节点从 `DB_PORT` 读取，发布前必须确认一致。
- 流程动作当前 `targetOrigin` 仍是 `*`，生产环境应配置门户 origin 白名单。
- 流程父页面还需要按 `actionId` 幂等消费并回传执行结果。
- localStorage 历史不能替代服务端审计。

## 7. 当前开发验收重点

1. `npm run build` 必须通过。
2. 制度问答验证 `差旅费包括哪些费用？`，确认 blocking、引用来源和 `<think>` 清洗。
3. 办公智能验证通知或会议纪要生成，确认 Agent SSE 增量和历史不保存思考内容。
4. 智能问数验证已支持的生产指标问题，确认真实 Dify 返回、失败 SQL 修复和图表输出；同时核对已发布版本与最新草稿的差异。
5. 流程助手验证 `打开采购请示单`，确认只有用户点击卡片后才发送 `IGIX_AI_ACTION`。
6. 在真实 iGIX 门户验收窗口协议、当前用户握手、动作幂等和采购请示单打开。
7. 在完成 Dify HTTP + AI Gateway 改造前，不得移除现有 Dify 直连回退和前端能力。

## 9. 后续优先级

1. 在 Dify 控制台确认智能问数最新草稿的端口、变量和工具参数，确认无误后再发布。
2. 统一 Dify、前端和 AI Gateway 的用户身份链路，先完成服务端授权，再考虑移除浏览器可见的 Dify Key。
3. 补齐门户 origin 白名单、动作执行回执和审计落库联调。
4. 对所有 `pending` 流程入口逐项实测，只有真实验证通过后才改为 `verified`。
5. 智能填单必须先完成真实表单侧 `BindingData.setValue` 桥接，再单独开启字段预填。
