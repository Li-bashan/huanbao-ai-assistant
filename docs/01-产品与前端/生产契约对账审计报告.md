## 2. v2 协议层级实测对账

### 2.1 版本结论

协议版本确定为 `2.0`，不是推测值：

- 后端 `PresentationResponseV2.PROTOCOL_VERSION` 固定为 `"2.0"`。
- 前端 `DATA_QUERY_PROTOCOL_VERSION` 固定为 `"2.0"`。
- `DataQueryResult.vue` 只有在 `protocolVersion === "2.0"` 且 `protocolValid === true` 时才进入结构化卡片。

### 2.2 顶层与 content 的真实归属

后端 `ContentV2` 的真实字段为 `title`、`summary`、`metrics`、`table`、`chart`、`insights`、`evidence`、`dataInfo`、`followUps`；`PresentationResponseV2` 把这个对象挂在顶层 `content`。前端 `normalizeContent(candidate.content)` 也只从 `candidate.content` 读取这些字段，组件实际读取的是 `protocol.content`。

| JSON 路径 | 实测字段 | 结论 |
|---|---|---|
| 根对象 | `protocolVersion`、`requestId`、`conversationId`、`status`、`messageType`、`analysisType`、`clarification`、`meta` | 顶层协议控制字段 |
| `content` | `title`、`summary`、`metrics`、`table`、`chart`、`insights`、`evidence`、`dataInfo`、`followUps` | 结构化内容严格由 content 承载 |
| `content.dataInfo` | 数据口径、范围、统计、来源、校验 | 不是根对象字段，也不是 meta 字段 |
| `meta` | 审计和降级元数据 | 与 content 同级，不能用来替代 content |

这里的严格含义需要说清楚：当前后端发出的 v2 对象没有把上述内容字段平铺到根对象；当前前端也不会从根对象读取 `title`、`metrics` 等字段。若 `content` 缺失或不是对象，归一化器会记录 `content must be an object` 并关闭结构化渲染。前端没有做“额外根字段禁止出现”的完整 JSON Schema 拒绝，因此未来若有人额外发送根级 `title`，它会被忽略而不是被单独报错；这不构成根级字段得到支持。

### 2.3 meta 与数据口径字段的实际挂载位置

后端 `MetaDto` 的字段只有：

```text
meta.auditStatus
meta.validated
meta.auditSummary
meta.analysisState
meta.analysisCoverage
meta.degraded
meta.degradedMessage
```

`dataCutoffDate` 和 `indicatorName` 的实际位置是 `content.dataInfo.dataCutoffDate`、`content.dataInfo.indicatorName`。同一对象还包含 `analysisType`、`indicatorCode`、`unit`、`timeRange`、`aggregation`、`organizationScope`、`rowCount`、`statistics`、`comparison`、`sourceTables`、`warnings`、`coverage`、`validation`。

`periodLabel` 没有在当前后端 `DataInfoDto`、前端 `normalizeDataInfo`、接口说明或直接协议测试中找到定义，判定为 `NOT_VERIFIED`。当前可用的时间结构是 `content.dataInfo.timeRange`，内部字段为 `expression`、`start`、`end`、`endExclusive`。

### 2.4 一个已发现的状态命名偏差

后端 `PresentationResponseV2` 产生的无数据状态是 `NO_DATA`；`DataQueryResult.vue` 的状态文案判断检查的是 `NO_DATA_IN_PERIOD`。这不会破坏 summary、表格空态或降级链路，但会导致后端 `NO_DATA` 在该文案分支中显示为“需要处理”。在补 UI 之前必须先冻结唯一状态枚举或建立明确兼容映射；本任务不修改业务代码。

## 3. analysisType 端到端支持盘点

判定口径：只把后端拥有可达的执行分支、数据结构和语义映射的类型判为 `SUPPORTED`。前端 Set 中列出一个枚举、协议装配器能接受一个字符串，不能单独证明该类型已经上线。

| analysisType | 四态判定 | 实测代码事实 | 前端/施工结论 |
|---|---|---|---|
| `FACT` | `SUPPORTED` | `IntentClassifier`、`ConversationStateManager` 和 pipeline 都有默认事实查询路径；输出有 metrics/table/chart/evidence/dataInfo/followUps。 | 可沿用现有 v2 卡片，但仍需真实授权用户回归。 |
| `DETAIL` | `PARTIAL` | 前端协议枚举和 `ProtocolAssembler.protocolAnalysisType` 接受它；装配器只有通用周期、对象、指标、数值表，没有 detail 专用路由或明细字段族；路由和会话状态允许集合不含它。 | 只能按通用结果降级，不能设计明细专用视图。 |
| `TREND` | `SUPPORTED` | 路由允许；pipeline 在非排名路径输出目标周期序列，调用 `buildTrendChart`，并计算同比/环比；多主体趋势还有异常关注文本。 | 可使用现有趋势图和明细，但异常仍不是独立结构。 |
| `RANKING` | `SUPPORTED` | 路由允许；pipeline 有 ranking 分支、排名计算、排名图和 `rank`/`previousRank`/`rankChange` 事实字段。 | 可使用现有排名表/图，集团排名仍必须服从服务端授权。 |
| `COMPARISON` | `PARTIAL` | 会话状态能识别同比/环比，`DataInfoDto.comparison` 也有布尔口径，事实行带同比/环比字段；但没有独立 comparison 执行分支，结果通常仍是 FACT 或 TREND。 | 不能假设存在双轴、基期对照或独立对比摘要。 |
| `ANOMALY` | `PARTIAL` | `AnalysisEngine` 有异常算法；pipeline 仅在 `analysisType=TREND` 且主体数大于 1 时执行，并把命中主体拼成 `insights` 中的 `attention` 文本。没有 anomaly DTO、阈值、异常点序列或独立 evidence 结构。 | 只能展示“需进一步核实”的通用关注文本，禁止异常专用视图承诺。 |
| `DRILLDOWN` | `NOT_SUPPORTED` | 前端 Set 和装配器枚举接受该值，但路由、pipeline 和 protocol DTO 没有下钻分支、层级节点、父子维度或下钻结果结构。 | 不得编码下钻导航或下钻树。 |
| `OVERVIEW` | `PARTIAL` | `ProtocolAssembler` 可把 `OVERVIEW`、`REPORT`、`COMPOSITE` 映射成 overview 标题；内部 pipeline 对 `COMPOSITE`/`REPORT` 可生成 `documentMarkdown`。但 v2 没有 `content.sections[]`，也没有领导视角分段 DTO。 | 只能把它看成通用结果加简报 summary，领导驾驶舱视图必须等契约补齐。 |
| `RANKING_COMPARISON` | `NOT_SUPPORTED` | 内部 `RankingItem` 有可复用的 `previousRank`/`rankChange`，但排名计算只在 `analysisType=RANKING` 调用；没有该类型的路由、执行分支、专用表列或比较摘要。 | 可复用字段不等于该类型已支持；暂不做同比排名专用组件。 |
| `DISTRIBUTION` | `NOT_SUPPORTED` | `AnalysisEngine` 单独有 `DistributionResult`、P25/中位数/P75 和极值标记测试，但 `/api/query/execute` 的 pipeline 没有调用它，`ContentV2` 也没有 distribution 字段或 assembler 映射。 | 内核算法资产不能当作公开协议；暂不做分布图或分布统计卡。 |

### 3.1 路由层与协议层的错位

前端 `DATA_QUERY_ANALYSIS_TYPES` 目前一次性列出了 10 个值，后端 `ProtocolAssembler` 的展示归一化也列出了 10 个值；但 `IntentClassifier.ANALYSIS_TYPES` 和 `ConversationStateManager.normalizeAnalysisType` 实际只允许 `FACT`、`RANKING`、`TREND`、`REPORT`。因此，前端枚举是容错/预留列表，不是 10 类后端生产能力清单。任何新视图必须先依赖后端可达的正向样例和错误样例，不能根据枚举名称施工。

## 4. 高阶字段与协同能力核查

### 4.1 OVERVIEW 与领导视角分段

未发现 `content.sections[]`。当前 overview 证据只有：`REPORT`/`COMPOSITE` 到 `OVERVIEW` 的字符串映射、`documentMarkdown` 作为 summary、通用 metrics/table/chart/insights/evidence。未发现“经营总览、风险、建议、待办”等领导视角分段的 DTO、JSON schema 或渲染协议。

结论：`OVERVIEW = PARTIAL`。后续策略是先固定 sections 的服务端 schema 和空态规则，再做领导视图；在此之前只能渲染现有 content 字段。

### 4.2 DRILLDOWN / DIAGNOSIS 与归因指标

未发现 `relatedMetrics[]`、归因树、驱动指标集合或下钻节点结构。后端 `EvidenceV2Dto` 只有单数 `relatedMetric`，它仅服务于 `correlatedClues`；原因类问题会加入“变化原因仅作为相关线索”的 pending 文本，不会产出因果诊断结构。

`DIAGNOSIS` 也不在当前 10 个 `analysisType` 枚举中，代码和接口说明没有直接定义，判为 `NOT_VERIFIED`。因此不能把通用文本中的“原因”渲染成诊断结论，也不能提前做 related metrics 面板。

### 4.3 composite_data_to_doc

结论：`PARTIAL`，但“公开 Gateway/Master 服务端接口”这一子项当前为 `NOT_SUPPORTED`。

- `huanbao-dataquery` 内部有 `DataToDocPipelineService`，`COMPOSITE`/`REPORT` 会触发文档生成，内部入口是 `/api/query/execute`。
- AI Gateway 的公开路由表只有独立的 `/api/ai/data-query/chat`、`/api/ai/office/chat` 和 `/api/ai/master/chat`，没有 `/api/ai/composite...` 或命名为 `composite_data_to_doc` 的 Gateway 契约。
- `DifyMasterChatService` 只代理 Master 的一个 streaming chat 请求，并把 `auth_context_json`、`analysis_state`、clarification 等输入传给 Dify；代码没有对 `composite_data_to_doc` 做服务端分支编排。

执行策略：在没有公开接口、请求/响应 schema、超时、失败回滚和真实 SSE 样例前，前端不新增组合编排入口；若将来启用，必须以 Gateway 契约测试为先，并把文档生成失败降级为已核验数据，而不是伪装成完整简报。

### 4.4 workflow_audit_api

结论：`PARTIAL`。

已有：`POST/GET /api/ai/action-audits`、`ActionAuditCreateRequest`、DDL 和 `action_id` 唯一索引。缺失：

- request 没有 `ATTEMPT` 语义枚举或动作生命周期字段；`result` 只是任意字符串。
- Repository 是普通 `INSERT`，没有按同一 `actionId` 查回已有记录、`ON CONFLICT`、版本更新或幂等响应。唯一索引只会让重复写入失败，不等于同一 actionId 幂等。
- `sendIgixAction` 只向父页面发 `IGIX_AI_ACTION`，前端没有调用该审计接口。
- Controller 当前没有管理员或签名身份访问控制，接口说明也明确写了需补鉴权。

执行策略：在服务端补齐“发送前 ATTEMPT 预记账、ACK/成功/失败状态更新、同 actionId 返回同一审计事实、鉴权和字段白名单”之前，不得在 UI 显示已办理成功，也不得把 postMessage 成功当作业务完成。

### 4.5 portal_ack

结论：`NOT_VERIFIED`，宿主验收标签为 `HOST_PENDING`。

当前 `actionBridge.js` 会解析目标 Origin、清洗 payload、生成新的 UUID `actionId`，然后发送：

```text
{ type: "IGIX_AI_ACTION", payload: actionPayload }
```

仓库没有 `IGIX_AI_ACTION_ACK` 字面量、回执监听器、回执 schema 或父页面工程。助手侧存在用户信息回执的 Origin/source 校验，但那不是动作 ACK。当前仓库不含 iGIX 宿主工程，无法证明父页面支持 ACK 通信。

执行策略：标记 `HOST_PENDING`，在真实宿主中由父页面按 iframe source、Origin 和 actionId 验证回执；没有 ACK 前，助手只显示“已发送/等待门户处理”，不能显示“已完成”。

### 4.6 File Hub

结论：`NOT_VERIFIED`。当前代码、Gateway 接口说明和协议 DTO 中没有 File Hub、文件中心或附件中心的直接定义。

执行策略：不把文件上传、文件引用、权限继承或文件导出写进当前视图；需要时另立接口契约和安全评审。

## 5. ACCESS_AND_SECURITY 对账

结论：`PARTIAL`，因此 MUST_HAVE Gate 不通过。

| 安全项 | 当前实测事实 | 状态 |
|---|---|---|
| 用户身份 | Gateway 默认配置为 `SIGNED_HEADER`；`DataQueryIdentityService` 校验 `X-Portal-Identity`、时间戳和 HMAC-SHA256，并要求签名身份解析出 userId/userName。 | 已有，但生产密钥/实际门户签名仍需现场验证 |
| 用户 DataScope | `DataQueryAccessService` 按 tenantId + userId 查服务端授权，得到组织范围、指标范围、集团排名和全组织标记；Gateway 将 `allowedOrgCodes` 传给内部问数服务，内部 `KingbaseQueryExecutor` 会绑定 `allowedOrgs` 并在根 WHERE 注入组织范围。 | 组织范围链路有；整体 DataScope 不完整 |
| 指标范围 | `allowedIndicatorCodes` 在授权 DTO、管理接口和数据库模型中存在，但 `DataQueryChatController` 没有把它传给内部问数服务，执行服务也没有消费该授权字段。 | 缺失 |
| 集团排名/全组织权限 | `allowGroupRanking`、`allowAllOrganizations` 存在于授权模型和 access 响应，但没有随 `/api/query/execute` 请求传递或在执行分支中核验。 | 缺失 |
| Origin 来源校验 | 前端 postMessage 使用解析出的目标 Origin，用户回执校验 source/origin；但 Gateway `CorsConfig` 是 `allowedOriginPatterns("*")`，`DataQueryIdentityService` 未按请求 Origin 做白名单校验。 | 缺失 |
| 浏览器身份可信度 | 浏览器 body 中的 `untrustedClientContext` 在签名模式不覆盖服务端身份；但 `PERMISSIVE`/`BODY_TRIAL` 兼容模式仍存在，生产必须确保配置关闭。 | 条件成立 |

因此，`ACCESS_AND_SECURITY` 不能写成“已完成安全闭环”。施工 Gate 必须把用户 DataScope 的所有授权维度、签名身份、Origin 白名单和生产配置验证作为一个整体，不允许只凭“有 HMAC”放行。

## 6. 前端渲染降级防线

当前实现已经有以下防线，后续界面施工必须保持：

1. 结构化入口由 `protocolVersion === "2.0" && protocolValid === true` 双条件控制。版本不符、字段校验失败或缺少 content 时，不进入结构化分析卡片。
2. v2 校验失败时仅展示 `protocol.content.summary` 或可信 fallback answer；非 v2 结果走旧的 Markdown/排名表兼容渲染。不能因为解析失败而自行猜测指标、组织、数字或 analysisType。
3. 归一化器只从 `content` 取 title、summary、metrics、table、chart、insights、evidence、dataInfo、followUps；不存在的字段变为空集合或 null。没有 `sections`、`relatedMetrics`、distribution 专用结构时，前端不得凭文本制造这些组件。
4. 数据规模有上限：metrics 最多 12 个，table columns 最多 40 个、rows 最多 1000 行，chart series 最多 12 组、单组 data/category 最多 1000 个，insights/evidence 最多 8 条，followUps 最多 6 条。
5. 文本归一化会去除 `<think>`，结构化单元格、CSV 和 Markdown 继续使用现有安全渲染/导出链路；任何新增字段必须先定义安全边界。
6. `meta` 只能作为状态、审计和降级元数据使用；`dataCutoffDate`、`indicatorName` 等数据口径只能从 `content.dataInfo` 取。不能把 meta 中不存在的 `periodLabel` 当作必有字段。
7. 由于当前后端 `NO_DATA` 与前端 `NO_DATA_IN_PERIOD` 存在命名偏差，后续视图必须保留未知状态的中性文案和空数据降级，直到状态枚举统一。
8. 前端对 10 类 analysisType 预留了中文标签，但标签映射不代表能力已上线。新组件必须以本报告的能力 Gate 为准，不得以标签或枚举 Set 为准。

## 7. 强制施工 Gate 与执行矩阵

四态含义：

- `SUPPORTED`：后端有完整可达数据结构及语义映射。
- `PARTIAL`：已有部分基础结构或算法，但缺少独立语义、字段、路由或安全闭环。
- `NOT_SUPPORTED`：没有当前公开契约所需的专用后端结构/执行分支。
- `NOT_VERIFIED`：当前代码或接口说明没有直接定义，不能假设存在。

### 7.1 MUST_HAVE（核心必达）

| Gate 能力 | 当前状态 | 准入判定 | 放行条件 |
|---|---|---|---|
| FACT | `SUPPORTED` | 条件放行 | 用真实授权身份完成正向、无数据、协议损坏三类回归。 |
| TREND | `SUPPORTED` | 条件放行 | 验证多周期、基期缺失、异常关注和图表降级。 |
| RANKING | `SUPPORTED` | 条件放行 | 验证组织 DataScope、完整授权主体、排名和无数据主体。 |
| COMPARISON | `PARTIAL` | 阻断 | 固定独立对比语义、基期结构和 response 样例。 |
| ANOMALY | `PARTIAL` | 阻断 | 固定异常点/阈值/证据结构，不能只返回 attention 文本。 |
| OVERVIEW | `PARTIAL` | 阻断 | 定义 `content.sections[]` 和领导视角分段 schema，并提供空态。 |
| DRILLDOWN | `NOT_SUPPORTED` | 阻断 | 后端提供下钻路由、层级结构和权限继承契约。 |
| ACCESS_AND_SECURITY | `PARTIAL` | 阻断 | 同时闭合用户 DataScope 全维度、签名、Origin 白名单和生产配置实测。 |

MUST_HAVE 总 Gate：`FAIL / BLOCKED_FOR_VIEW_CODING`。在上述阻断项关闭前，不开始任何依赖这些假设的界面或视图编码。

### 7.2 CONDITIONAL / OPTIONAL（条件与可选）

| 能力 | 当前状态 | 执行策略 |
|---|---|---|

## 8. 后续验收最小清单

- 对 FACT、TREND、RANKING 各保存一个真实 Gateway SSE `analysis_result` 样例，确认根字段和 content 路径。
- 对 COMPARISON、ANOMALY、OVERVIEW、DRILLDOWN 做正向/不支持样例，证明服务端不会静默伪造类型。
- 对 `content.sections[]`、`relatedMetrics[]`、distribution 和 ranking comparison 要么拿到正式 schema，要么明确返回不支持。
- 使用有效签名身份核验 tenant/user DataScope，特别是 allowedIndicatorCodes、allowGroupRanking、allowAllOrganizations 是否真正进入执行边界。
- 在 Gateway 侧以真实 Origin 验证白名单和 CORS 行为；在 iGIX 宿主侧验证 `IGIX_AI_ACTION_ACK`。
- 对动作审计验证 ATTEMPT 先写、ACK 后更新、同 actionId 重试返回同一审计事实，而不是第二条记录或数据库唯一键异常。
- 继续保留 `npm run build`、协议损坏归一化和现有历史/导出回归。
