# 浪潮原生智能能力动态发现机制研究

更新时间：2026-08-28

## 一、结论先说

你的判断基本是对的：如果让环宝助手自己维护所有菜单、所有表单和所有字段的静态映射，工作量会越来越大，这不是浪潮原生体系的主要工作方式。

但原生也不是完全零配置。它采用的是三层机制：

1. **菜单目录动态发现**：运行时从平台函数目录加载当前登录用户可访问的功能，菜单发布和授权变化后可以进入目录，不需要在前端硬编码全量菜单。
2. **表单技术字段动态读取**：智能填单配置页通过平台元数据服务读取表单、业务对象和字段属性，字段编号、字段名称、数据类型、是否必填等信息可以自动带出来。
3. **业务语义和填报范围配置**：管理员仍然要在智能填单配置中选择某个表单，选择允许 AI 填报的字段，补充表单描述、智能体提示词等。这是业务边界配置，不是开发人员逐字段编写 JavaScript 映射。

最关键的边界是：

> 菜单和字段元数据可以动态发现，哪些字段允许被 AI 填、这些字段在业务上代表什么，以及最终如何安全写入运行中的表单，仍然需要配置或由表单运行时桥接负责。

## 二、服务器反向分析证据

服务器目录：

```text
/home/GSCloud/web
```

### 2.1 智能填单配置模块不是手写字段表

服务器存在独立的智能填单配置模块：

```text
/platform/runtime/bcc/web/aifillform-config/
```

其中的 API 资源文件：

```text
/platform/runtime/bcc/web/aifillform-config/js/api.js
```

该文件暴露的关键请求关系如下：

```js
// 表单候选，来自运行时元数据服务
GET /api/runtime/lcm/v1.0/rt-metadatas/helper?metadataTypes=Form,MobileForm

// 根据表单元数据 ID 获取表单字段属性
GET /api/runtime/bcc/v1.0/aifillformConfig/form/{id}

// 菜单候选，来自平台功能目录
GET /api/runtime/sys/v1.0/functions/allFunctions?needSort=true

// 保存智能填单配置
POST /api/runtime/bcc/v1.0/aifillformConfig

// 修改智能填单配置
PUT /api/runtime/bcc/v1.0/aifillformConfig

// 根据配置 ID 读取已经保存的配置
GET /api/runtime/bcc/v1.0/aifillformConfig/config/{id}

// 根据表单和字段生成智能体提示词
POST /api/runtime/bcc/v1.0/aifillformConfig/agentprompt

// 根据表单和字段生成智能应用描述
POST /api/runtime/bcc/v1.0/aifillformConfig/aiappdesc
```

这里已经能回答两个核心问题：

- **有哪些表单**，通过表单元数据服务读取，不是手工录入一张表。
- **有哪些菜单**，通过平台函数目录读取，不是由 `rtfOpenMenu` 自己维护一张表。

### 2.2 配置页的字段模型

服务器 `configPage.js` 中的表单模型包含：

```js
formInfo: {
  formId: '',
  formName: '',
  formDescription: '',
  viewObjectId: '',
  fieldPropertyList: []
}

menuInfo: {
  menuId: '',
  menuName: '',
  menuType: ''
}
```

字段列表展示的属性包括：

| 属性 | 作用 |
| --- | --- |
| `code` | 字段编号，技术写入和识别的基础标识 |
| `name` | 字段名称，给管理员和模型看的业务名称 |
| `dataType` | 文本、整数、浮点、布尔、日期、日期时间等 |
| `objectType` | 普通字段、枚举、关联等对象类型 |
| `isRequired` | 是否必填 |
| `isMultiSelect` | 是否多选 |
| `isFill` | 是否允许智能填报 |
| `description` | 字段描述，可用于模型理解业务含义 |

这说明原生智能填单的技术字段清单不是开发人员手写出来的，而是从表单元数据中加载出来的。管理员在配置页中对字段做的是选择和补充描述。

### 2.3 原生配置仍然需要什么

服务器配置页保存前会检查：

- 必须选择表单；
- 至少选择一个 `isFill` 字段；
- 必须填写表单描述；
- 必须选择菜单和菜单类型；
- 必须填写智能体提示词；
- 必须填写智能应用描述。

所以，原生方案并不是用户今天新建一个表单，明天新建一个表单，智能填单配置就完全不用碰。新表单第一次纳入智能填单能力时，仍然需要建立一条智能填单业务配置。

但这条配置不是下面这种笨重的开发映射：

```js
{
  formCode: '某个表单',
  fields: {
    用户说的项目名称: ['某个内部路径'],
    用户说的联系人: ['另一个内部路径']
  }
}
```

而更接近：

```js
{
  formInfo: {
    formId: '平台表单元数据 ID',
    fieldPropertyList: [
      {
        code: 'projectName',
        name: '项目名称',
        dataType: 'String',
        isFill: true,
        description: '本次业务项目的名称'
      }
    ]
  },
  menuInfo: {
    menuId: '平台菜单 UUID'
  },
  formDescription: '请假申请表，用于员工提交请假和出差相关信息',
  agentPrompt: '只填充用户明确提供且允许填报的字段，不自动提交'
}
```

前者要求开发人员维护每个字段的路径和语义，后者由平台先把字段属性自动加载出来，管理员只维护 AI 的业务范围和说明。

## 三、菜单到底如何被发现

### 3.1 平台运行时的菜单目录

服务器运行时主程序会调用函数服务加载应用和功能，并将结果放入运行时缓存：

```js
window.GSP_RTF_FUNCSINFO
```

运行时中可以看到：

```js
functionService.loadApps()
```

以及平台函数目录接口：

```text
/api/runtime/sys/v1.0/functions/allFunctions
/api/runtime/sys/v1.0/functions/{id}
/api/runtime/sys/v1.0/functions/funcInvok/{id}
```

其中：

- `allFunctions` 用于取得功能目录；
- 单个 `{id}` 用于按功能 ID 补充功能实体；
- `funcInvok/{id}` 用于取得具体功能的调用配置、URL、静态参数和实体参数；
- 返回结果受当前登录用户权限影响，不能把它当成全平台不加权限的公开目录。

### 3.2 `rtfOpenMenu` 自己不负责查目录

服务器文件：

```text
/platform/runtime/sys/web/rtfwidget/rtfopenmenu.js
```

这个部件接收宿主传入的：

```js
vueState.data.funcList
```

用户点击某个候选后，它最终调用：

```js
window.top.gspframeworkService.rtf.func.openMenu({
  funcId: item.id,
  tabId: item.tabId,
  appType: 'menu'
})
```

因此 `rtfOpenMenu` 是执行器和展示器，不是菜单搜索数据库。菜单候选由上游的运行时上下文、平台导航服务或原生助手服务提供。

### 3.3 原生助手还会接收当前功能关系

原生智能助手使用的接口包括：

```text
POST /api/runtime/sys/v1.0/ast/manager/component/paging
GET  /api/runtime/sys/v1.0/ast/manager/intelligentassistant/id/{assistantId}
GET  /api/runtime/sys/v1.0/ast/manager/intelligentassistant/funcrel
```

其中 `funcrel` 返回功能和助手之间的关系，原生助手据此决定当前功能对应哪个助手配置。它不是在前端写死“采购菜单对应哪个助手”，而是由平台配置返回关系。

## 四、字段到底如何被原生助手知道

这里必须区分两个角色。

### 4.1 智能填单配置模块知道字段

`aifillform-config` 明确会通过元数据服务取得表单候选，并通过表单接口取得字段属性列表：

```text
表单元数据服务
  -> 表单 ID、表单名称、业务对象、字段属性
  -> 配置页展示字段
  -> 管理员勾选 isFill 字段
  -> 保存 formInfo.fieldPropertyList
```

所以原生智能填单的字段认知来源是：

1. 低代码表单元数据；
2. 业务实体或视图对象的字段定义；
3. 管理员对可填范围和业务描述的配置。

### 4.2 `fillform` 展示包本身不知道字段

服务器文件：

```text
/platform/runtime/common/web/fillform/fillformwidget.js
```

它收到的 `data.fields` 已经是上游准备好的结果，主要负责：

- 展示字段名称和值；
- 展示追问和建议；
- 根据 `pcMenuId` 打开菜单。

它没有看到表单元数据查询、字段树构建、模型调用或 `BindingData` 写入逻辑。因此不能得出“把 `fillform` 嵌入环宝助手，它就会自动扫描任意表单字段”的结论。

### 4.3 原生助手的上下文通道

服务器文件：

```text
/platform/runtime/sys/web/intelligentassistant/assistant-intg-sdk.umd.js
```

SDK 提供：

```js
registerContextProvider(provider)
requestContext()
requestAndMergeContext()
pushCaptureContext(context)
getAssistantContext()
```

SDK 在当前页签上保存上下文提供者，并在助手提问时执行提供者，将 `FRAMEWORK`、`USER`、`CAPTURE` 三类数据合并后发给助手。原生助手默认会携带当前页签、当前功能、用户和页面捕获上下文。

这解释了原生助手为什么可以感知当前页面：它依赖运行时上下文通道，不是每个页面都在前端手写一份导航映射。

## 五、服务器中发现的 AI 表单描述接口线索

服务器智能问答资源中出现过：

```text
/api/runtime/sys/v1.0/aiFillForm/afterChat/formDescription/{dataId}/{metadataId}/{menuId}
```

同时，智能填单配置模块还提供：

```text
/api/runtime/bcc/v1.0/aifillformConfig/form/{id}
/api/runtime/bcc/v1.0/aifillformConfig/agentprompt
/api/runtime/bcc/v1.0/aifillformConfig/aiappdesc
```

这表明平台存在围绕表单描述、字段属性和智能体提示词的后端链路。

但是要保持严谨：目前通过服务器静态包确认了接口路径和调用关系，尚未在已登录浏览器中抓到该 `aiFillForm/afterChat/formDescription` 的真实请求和响应。因此不能直接把它承诺成环宝助手可调用的公开字段写入 API，也不能据此认为 `fillformwidget.js` 自己会调用它。

下一步应该在已登录环境中打开智能填单配置和真实表单，观察 Network：

1. 选择表单时是否请求 `rt-metadatas/helper`；
2. 选择具体表单时返回的 `fieldPropertyList` 完整程度；
3. 保存配置后，原生助手对话时是否请求 `aiFillForm/afterChat/formDescription`；
4. 原生助手最终通过哪个宿主或运行时通道把值写入表单。

## 六、新表单明天出现时，实际会发生什么

### 6.1 只要求菜单导航

如果明天发布了一个新菜单，并且当前用户有权限：

1. 菜单进入平台函数目录；
2. 运行时刷新或重新加载功能目录；
3. `GSP_RTF_FUNCSINFO` 和函数服务可以看到它；
4. 环宝助手通过目录搜索候选；
5. 用户确认后调用 `openMenu`。

这一类能力不需要环宝助手维护全量菜单映射。

### 6.2 要求智能填单

如果明天发布了一个新表单：

1. 表单元数据服务可以提供表单和字段属性；
2. 在原生智能填单配置页中选择该表单；
3. 平台自动带出字段编号、字段名称和数据类型；
4. 管理员勾选允许 AI 填报的字段；
5. 管理员补充表单描述和提示词；
6. 保存一条智能填单业务配置；
7. 原生智能能力才知道这个表单的业务范围和可填字段。

所以新表单并非完全不用配置，而是从“开发者写一堆代码映射”变成“平台元数据自动加载，管理员确认填报范围”。这已经把维护量从全量技术映射降到了业务配置量。

### 6.3 表单之间的跳转关系由平台元数据负责

表单、台账、审批详情之间的关系也不应该复制到环宝助手中。iGIX 运行时会根据功能调用配置取得目标 URL、静态参数和实体参数：

```text
funcId
  -> /api/runtime/sys/v1.0/functions/funcInvok/{funcId}
  -> invokingConfig.url
  -> staticParams / entityParams
  -> 打开目标页签和目标表单
```

流程详情、联查和从列表进入卡片时，平台会通过菜单配置、流程上下文和 `entityParams` 传递业务数据。环宝助手不需要维护“表单 A 一定跳表单 B”的全量关系表，只需要在动作发生时保留请求 ID，并让 iGIX 运行时完成目标页面路由。

只有当某个业务要求自然语言识别一个特殊关联动作，或者平台目录无法表达一个自定义入口时，才增加一个小型兼容规则。

## 七、对环宝助手的正确架构建议

### 7.1 取消全量菜单静态映射

环宝助手不应该继续把所有菜单都写入 `workflowActions.js`。应该增加一个动态功能目录适配器：

```text
当前登录门户
  -> 平台函数目录或父页面运行时上下文
  -> 当前用户可访问的功能列表
  -> 本地按名称、编号、应用、路径检索
  -> rtfClarification 处理歧义
  -> gspframeworkService.rtf.func.openMenu 执行
```

本地配置只保留：

- 特殊联查动作；
- 平台目录无法返回的兼容项；
- 业务别名和搜索权重；
- 测试环境的固定入口。

这些是增量配置，不是全量菜单清单。

### 7.2 取消每个表单必填的静态字段路径表

智能填单请求应该优先使用当前表单运行时提供的字段描述：

```text
当前表单
  -> 通用桥接器读取表单身份和字段描述
  -> 只暴露可见、可编辑、非只读字段
  -> 模型输出已验证的字段 code 和值
  -> 桥接器按字段元数据校验类型
  -> BindingData.setValue
  -> ACK
```

只要平台表单运行时能提供当前表单字段元数据，模型就可以直接使用真实字段 `code`，不需要开发人员为每个表单维护一套逻辑名称到路径的映射。

### 7.3 只保留小型的语义补充配置

仍然可能需要的配置不是全量字段映射，而是下面这些业务增强：

- “出差项目”是“项目名称”还是“出差事由”的别名；
- 某个关联字段需要通过人员 ID 或组织 ID 查询；
- 某个枚举字段的自然语言和枚举值转换；
- 某个表单禁止填报金额或敏感字段；
- 某个表单需要特殊的明细行处理。

这些配置是业务规则和安全边界，无法单纯依赖字段技术元数据自动推断。原则是只补充有歧义的地方，不把每个字段重新抄一遍。

### 7.4 真实字段写入仍要以表单运行时为准

本地手册已经确认 Farris-Angular 表单的正式写入入口是：

```ts
this.frameContext.bindingData.setValue(path, value, true, true)
```

因此，即使字段是动态发现的，也不能让模型直接生成任意路径并执行。通用桥接器至少要做：

1. 从当前表单运行时取得可用字段描述；
2. 校验字段 code 是否存在；
3. 校验字段是否可编辑；
4. 校验数据类型和枚举、关联对象格式；
5. 通过当前表单的 `BindingData` 写入；
6. 回读或监听变更结果；
7. 返回 `applied`、`partial` 或 `rejected` ACK。

## 八、对现有方案的修正

之前方案中 `formBridgeRegistry` 容易被理解成“所有表单都要逐项登记”，这个理解需要纠正：

- 它不能成为全量菜单注册表；
- 它不能要求每个表单都手写全部字段路径；
- `funcId` 优先从当前用户功能目录或运行时上下文获得；
- 字段列表优先从当前表单元数据或桥接器运行时读取；
- 注册表只保留别名、特殊值转换和安全覆盖项；
- 如果当前部署版本没有通用的表单字段元数据读取入口，才对个别表单增加最小兼容适配器。

最终目标不是消灭所有配置，而是把配置从全量技术映射降为：

```text
平台自动发现菜单
+
平台自动提供字段技术元数据
+
少量业务语义和安全规则
+
一个通用表单写入桥接器
```

## 九、当前能确认和不能确认的边界

### 已经确认

- 菜单目录存在平台函数服务和 `allFunctions` 接口；
- 运行时会缓存用户可用功能到 `GSP_RTF_FUNCSINFO`；
- `rtfOpenMenu` 接收上游传入的 `funcList`，自身不维护菜单目录；
- 智能填单配置页通过元数据接口取得表单和字段属性；
- 智能填单配置保存 `fieldPropertyList` 和 `isFill` 选择；
- 原生助手有 `registerContextProvider` 和 `requestAndMergeContext` 上下文机制；
- `fillformwidget.js` 本身不是字段元数据读取器，也不是 `BindingData` 写入器。

### 还需要真实浏览器验证

- `aiFillForm/afterChat/formDescription` 的真实响应格式；
- 当前部署版本是否向外提供通用的当前表单字段元数据接口；
- 原生智能体最终使用哪条消息或服务完成字段写入；
- 动态字段描述是否包含明细表、枚举、人员和组织字段的可写值格式；
- 新发布表单在功能目录和元数据缓存中的刷新时机。

## 十、最终判断

你不应该接受“先整理所有表单、菜单和字段映射”作为长期方案，那会把平台本来已经拥有的元数据能力重复造一遍。

合理路径是：

1. 菜单使用平台函数目录动态发现；
2. 表单使用平台元数据服务或当前表单运行时动态取得字段描述；
3. 模型只在可信字段描述范围内生成值；
4. 业务方只配置可填范围、描述和少量歧义规则；
5. 通用表单桥接器统一通过 `BindingData` 写入并返回 ACK；
6. 对确实没有通用元数据入口的特殊表单，再增加小型兼容适配器。

这样，新菜单不需要重新开发导航，新表单也不需要重新抄一整张字段映射表。真正需要人工判断的，是业务上哪些字段允许 AI 触碰，而不是平台技术上有哪些字段。
