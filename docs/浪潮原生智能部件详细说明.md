# 浪潮 iGIX 原生智能部件详细说明

更新时间：2026-08-27

## 1. 文档说明

本文对当前部署环境和部件管理页面中发现的 iGIX 原生智能部件进行逐项说明。

本文的目标不是把部件简单罗列出来，而是回答下面几个问题：

- 每个部件主要解决什么问题；
- 普通用户、业务人员、管理员和开发人员分别应该如何使用；
- 哪些部件适合接入环宝 AI 助手；
- 哪些部件适合调用其底层平台服务，而不适合直接显示；
- 哪些能力可以替代现有自定义开发；
- 哪些功能仍然需要在真实门户环境中验证；
- 这些部件和 Dify、iGIX 权限、当前用户信息之间如何分工。

## 2. 重要结论

### 2.1 这些部件已经部署，但不等于已经被业务应用使用

在服务器 iGIX 静态运行目录中已经发现相关运行资源，例如：

```text
/home/GSCloud/web/platform/runtime/sys/web/rtfwidget/
/home/GSCloud/web/platform/runtime/common/web/fillform/
/home/GSCloud/web/platform/runtime/wf/web/
/home/GSCloud/web/platform/runtime/epp/ink/widgets/
```

这说明平台已经具备这些原生能力，但部件管理页面的卡片只代表元部件或运行资源已经注册。只有把它配置到部件、页面、应用，或者由代码运行时加载，用户才会真正使用它。

### 2.2 原生部件不是普通 Vue 组件

iGIX 手册将元部件定义为前端代码级主体，部件是对元部件的配置和展示。一般使用路径是：

```text
业务公共
  -> 业务配置
  -> 工作中心
  -> 元部件或部件
  -> 页面设计器
```

因此，不能直接把 `sys / rtfOpenMenu` 当成 Vue 组件写成：

```js
import RtfOpenMenu from 'rtfOpenMenu'
```

环宝助手如果要在自己的 iframe 内使用这些部件，需要增加原生部件宿主、运行时脚本加载和生命周期适配。部分能力也可以直接使用 iGIX 框架服务，例如菜单打开服务。

### 2.3 环宝助手应该是唯一用户入口

最终用户只使用环宝 AI 助手，不能让用户在环宝助手、浪潮全局助手和多个悬浮入口之间选择。

建议：

- 关闭或隐藏平台原生的全局欢迎入口；
- 在环宝助手内部按场景加载原生部件；
- 原生部件只负责它擅长的菜单、表单、流程和平台交互；
- Dify 继续负责知识问答、办公智能、智能问数和自然语言理解；
- iGIX 继续负责用户、权限、菜单、表单和任务上下文。

## 4. 平台入口和导航类部件

## 4.1 `sys / rtf` 框架智能导航

### 部件信息

```text
中文名称：框架智能导航
命名空间：sys
部件编号：rtf
典型资源目录：/platform/runtime/sys/web/rtfwidget/
```

### 主要作用

`rtf` 是框架级导航能力，面向 iGIX 平台中的应用、菜单、工作中心和功能入口。它更像平台导航底座，不只是一个普通的菜单按钮。

它适合负责：

- 获取或展示用户可以访问的功能；
- 组织应用、模块、菜单、台账和看板；
- 支持平台级功能发现；
- 为其他菜单智能部件提供上下文；
- 处理菜单打开、标签页和门户导航关系。

### 在环宝助手中的使用方式

环宝助手可以把它作为菜单导航引擎：

```text
用户自然语言
  -> 环宝助手识别业务目标
  -> 从 iGIX 可访问菜单中查找候选
  -> 必要时调用 rtfClarification
  -> 调用 rtfOpenMenu 或 rtf.func.openMenu
```

### 适用用户

- 所有普通业务用户；
- 需要在多个业务模块中查找功能的用户；
- 不知道准确菜单名称的用户。

### 能替代的自定义工作

- 自己维护完整菜单树；
- 自己实现菜单打开和标签页逻辑；
- 自己维护大量菜单入口 UI；
- 自己处理部分框架导航状态。

### 注意事项

自然语言模型不能直接生成任意 `funcId`。菜单目标必须来自 iGIX 菜单目录、可信配置或平台接口。最终打开动作仍然必须由 iGIX 权限体系决定。

## 4.2 `sys / rtfOpenMenu` 菜单智能导航

### 部件信息

```text
中文名称：菜单智能导航
命名空间：sys
部件编号：rtfOpenMenu
典型资源文件：rtfopenmenu.js
```

### 主要作用

`rtfOpenMenu` 负责打开具体的菜单、台账、看板或功能页面。它是当前最适合优先接入环宝助手的原生部件。

它解决的是最终执行问题：用户已经确认了目标，平台需要按照 iGIX 的标签页、应用入口和权限规则打开页面。

### 底层调用方式

iGIX 手册提供了框架服务调用示例，核心方法是：

```js
const root = window.top || window

root.gspframeworkService.rtf.func.openMenu({
  appType: 'menu',
  funcId: '菜单功能UUID',
  appId: '',
  appEntrance: '',
  isNewTab: true,
  tabId: `ai_${Date.now()}`
})
```

其中：

- `appType` 为 `menu` 时表示打开菜单；
- `funcId` 应使用菜单 UUID；
- `isNewTab` 控制是否新开标签页；
- `tabId` 应该具有唯一性，避免连续点击被平台当成同一个标签页；
- `queryStringParams` 或 `entityParams` 可以用于传递特定上下文，但必须先验证目标页面是否支持。

此前的请假菜单可以这样打开：

```js
root.gspframeworkService.rtf.func.openMenu({
  appType: 'menu',
  funcId: '193545d8-29f9-4790-99f0-6c517aca3e4f',
  appId: '',
  appEntrance: '',
  isNewTab: true,
  tabId: `LeaveOpsList_${Date.now()}`
})
```

### 在环宝助手中的推荐位置

推荐将 `rtfOpenMenu` 作为动作执行器，而不是让用户单独打开它：

```text
用户：帮我打开请假台账
  -> 环宝助手识别目标
  -> rtf 或菜单解析能力返回目标
  -> rtfClarification 处理歧义
  -> rtfOpenMenu 执行打开
```

### 适用用户

所有需要打开平台功能的用户。

### 主要风险

- 只传菜单名称而不传 UUID；
- 大模型生成不存在的 UUID；
- 父页面和 iframe 同时执行，导致打开两次；
- `tabId` 不唯一，导致标签页复用异常；
- 没有校验消息来源，导致非可信页面触发平台动作。

## 4.3 `sys / rtfClarification` 应用澄清

### 部件信息

```text
中文名称：应用澄清
命名空间：sys
部件编号：rtfClarification
```

### 主要作用

用户输入通常不完整，例如：

```text
打开采购
打开请假
查一下项目
帮我处理一下报销
```

这些表达可能对应多个应用、表单、台账或业务模块。`rtfClarification` 的职责是把不明确的目标变成用户可以选择的明确目标。

### 在环宝助手中的使用方式

当候选数量大于一个，或者菜单、表单和台账之间存在歧义时展示澄清部件：

```text
请假相关入口
  - 请假申请
  - 请假台账
  - 请假审批
```

用户选择后再调用 `rtfOpenMenu` 或表单打开能力。

### 适用用户

所有普通业务用户，尤其是不了解系统菜单层级的用户。

### 能替代的自定义工作

- 自己写候选入口卡片；
- 自己写多结果选择逻辑；
- 自己处理用户选中目标后的回传。

### 验证重点

需要确认该部件支持的输入是菜单列表、应用列表、自然语言还是平台服务返回对象。目前本地手册中没有找到完整的公开参数说明，接入时应通过真实运行时和浏览器调试确认。

## 4.4 `sys / rtfQaWidget` 问答对部件

### 部件信息

```text
中文名称：问答对部件
命名空间：sys
部件编号：rtfQaWidget
典型资源文件：rtfqawidget.js
```

### 主要作用

从部件名称和运行时行为看，它更偏向平台问答对、固定问答和快捷问答能力，而不一定等价于一个完整的流式 AI 聊天窗口。

它适合承载：

- 高频固定问题；
- 平台配置的问答对；
- 操作指引；
- 常用问题快捷入口；
- 快捷命令触发。

### 与现有 Dify 的关系

当前环宝助手的制度问答和办公智能由 Dify 提供。`rtfQaWidget` 不应直接替代 Dify，除非确认它可以接入相同的知识库、会话、引用和流式返回协议。

推荐分工：

```text
固定问题、快捷问题、平台提示 -> rtfQaWidget
开放问答、知识检索、引用来源 -> Dify
```

服务端运行文件中可以看到它与平台助手集成 SDK 存在关联，配置中可能涉及问答标识，例如 `aiCenterQaId`。这说明它更依赖 iGIX 平台的智能服务配置，而不是直接复用环宝项目的 Dify Key。

### 适用用户

所有业务用户，但建议作为快捷问答区域，而不是首页唯一聊天能力。

### 验证重点

- 问答对数据在哪里配置；
- 是否支持动态传入当前用户；
- 是否支持环宝助手的主题样式；
- 是否支持点击答案后触发菜单或表单；
- 是否会自动显示独立的浪潮助手入口；
- 是否依赖平台智能中心配置。

## 4.5 `sys / rtfastwelcome` 助手欢迎部件

### 部件信息

```text
中文名称：助手欢迎部件
命名空间：sys
部件编号：rtfastwelcome
典型资源文件：rtfastwelcome.js
```

### 主要作用

负责助手开场时的欢迎信息、能力推荐和智能服务入口展示。

它可能适合展示：

- 欢迎文案；
- 常用能力；
- 智能服务列表；
- 助手推荐问题；
- 打开菜单或其他智能服务的快捷入口。

运行时文件中的命名和配置线索显示，它可能支持助手标识、智能服务列表以及自定义配置，例如：

```text
assistantId
intelligentServiceArr
widgetCustomOptions
```

这些参数的具体格式仍需要以当前部署版本的运行时行为为准。

### 在环宝助手中的使用方式

建议把它放入环宝助手自己的欢迎区域，由环宝助手负责外层标题、历史和对话状态。不要让它再创建一个新的全局助手窗口。

### 与当前项目的关系

当前项目已经有自定义欢迎卡片和能力选择器，因此接入时要做替换或封装，不能两套欢迎界面同时展示。

## 4.6 `sys / agentwelcomewidget` 智能体开屏欢迎部件

### 部件信息

```text
中文名称：智能体开屏欢迎部件
命名空间：sys
部件编号：agentwelcomewidget
典型资源文件：agentwelcomewidget.js
```

### 主要作用

从名称看，该部件偏向智能体开屏、智能体推荐和智能服务选择。它和 `rtfastwelcome` 都涉及助手欢迎区，因此产品上不建议同时启用。

### 与 `rtfastwelcome` 的区别处理

部件管理页面显示的注册信息和运行包内声明可能存在差异，尤其是命名空间或大小写。截图显示为 `sys / agentwelcomewidget`，运行文件元信息可能显示其他内部命名空间，因此最终应以当前环境中部件初始化时的实际注册信息为准。

如果平台管理页面还显示 `rtfAstWelcome`，本文暂按截图中的 `rtfastwelcome` 记录，必须现场确认是否只是大小写差异，还是两个不同部件。

### 产品建议

对 `rtfastwelcome` 和 `agentwelcomewidget` 做同一页面的对比验证：

- 加载速度；
- 欢迎效果；
- 能力列表配置；
- 是否带平台全局入口；
- 是否支持自定义点击事件；
- 是否支持在环宝 iframe 中运行。

最终只保留一个作为环宝助手主欢迎部件。

## 5. 业务办理和流程类部件

## 5.1 `rtcommon / fillform` 智能填单助手

### 部件信息

```text
中文名称：智能填单助手
命名空间：rtcommon
部件编号：fillform
典型资源目录：/platform/runtime/common/web/fillform/
```

### 主要作用

根据用户自然语言、当前用户信息、业务上下文和表单元数据，将内容填入 iGIX 表单。

适合的用户表达包括：

```text
帮我新建采购请示单
项目名称填污水处理改造
联系人用我自己
联系电话使用我的手机号
预算填 50000 元
```

### 推荐交互

智能填单不能直接执行并自动提交，推荐流程是：

```text
用户表达
  -> 环宝助手识别表单
  -> 读取当前用户白名单信息
  -> 解析字段和值
  -> 展示填充预览
  -> 用户确认
  -> fillform 执行填充
  -> 用户检查表单
  -> 用户自行提交
```

### 与当前项目的关系

当前项目已经保留了表单字段解析能力，但配置为：

```js
export const ENABLE_WORKFLOW_PREFILL = false
```

这说明项目目前主动关闭了预填充。接入 `fillform` 后需要重新确认：

- 字段名称和字段编码如何映射；
- 表单页面如何接收填充值；
- 当前用户信息如何传入；
- 表单上下文如何保持；
- 填充失败如何回滚；
- 是否支持明细表；
- 是否支持日期、金额、枚举和组织字段；
- 是否存在自动提交行为。

### 适用用户

需要发起业务表单的普通业务用户。

### 主要风险

- 字段填错；
- 当前用户信息填错；
- 大模型将普通文本当作字段编码；
- 明细数据覆盖原有数据；
- 未经确认直接提交；
- 填单动作绕过表单权限。

## 5.2 `sys / modifyformmessage` 智能组件操作确认按钮

### 部件信息

```text
中文名称：智能组件操作确认按钮
命名空间：sys
部件编号：modifyformmessage
```

### 主要作用

为智能修改、智能填单或其他表单操作提供确认入口。它解决的是人机交互中的最后一步确认问题。

### 推荐使用场景

- 确认填充采购请示单；
- 确认修改联系人或联系电话；
- 确认批量修改业务字段；
- 确认智能建议即将写入表单。

### 推荐显示内容

```text
即将填充：
项目名称：污水处理改造
联系人：当前登录用户
联系电话：当前用户手机号

[确认填充] [取消]
```

### 产品规则

`modifyformmessage` 应当和 `fillform` 配套使用，不应当成为绕过确认的装饰按钮。高风险动作必须明确显示动作对象、字段和值。

## 5.3 `task / taskSearch` 工作流任务查询部件

### 部件信息

```text
中文名称：工作流任务查询部件
命名空间：task
部件编号：taskSearch
```

### 主要作用

面向待办、已办、待阅和流程任务查询，适合处理：

```text
我有哪些待办
有哪些单据需要我审批
最近退回了哪些流程
查询我发起的流程
```

### 在环宝助手中的使用方式

用户提出任务类问题时，环宝助手加载该部件或调用其任务查询能力，结果展示在助手面板内。用户点击某条任务后，再通过 iGIX 菜单或任务上下文打开对应页面。

### 适用用户

所有有流程任务的业务用户。

### 权限要求

任务查询必须使用当前登录用户上下文，不能在前端手工拼接其他人的任务查询条件。最终数据范围由 iGIX 工作流权限决定。

## 5.4 `workflow / wf` 工作流智能助手

### 部件信息

```text
中文名称：工作流智能助手
命名空间：workflow
部件编号：wf
```

### 主要作用

面向流程办理、流程节点和工作流上下文的智能辅助。它比单纯任务查询更接近流程办理助手。

适合：

- 辅助理解当前流程；
- 查询流程状态；
- 提示下一步办理动作；
- 辅助处理流程任务；
- 在流程页面中展示上下文帮助。

### 在环宝助手中的使用方式

只有当用户进入流程场景，或者明确询问流程办理时，才加载 `wf`。普通制度问答和普通菜单导航不需要加载它。

### 需要验证的内容

- 是否依赖特定流程页面上下文；
- 是否支持嵌入 iframe；
- 是否支持从环宝助手传入流程实例 ID；
- 是否只能在 iGIX 工作流页面中运行；
- 是否允许环宝助手统一接管展示结果。

## 6. 流程设计和优化类部件

## 6.1 `bpm / BpmDrawingAIAssistant` 业务流智能绘图助手

### 部件信息

```text
中文名称：业务流智能绘图助手
命名空间：bpm
部件编号：BpmDrawingAIAssistant
```

### 主要作用

面向业务流或流程图的智能生成、绘制和辅助调整。

## 9. 部件的接入方式

### 9.1 方式一：通过 iGIX 页面和部件配置使用

适合验证部件自身功能：

```text
业务公共
  -> 业务配置
  -> 工作中心
  -> 部件
  -> 新增部件
  -> 选择对应元部件
  -> 配置
  -> 放入页面设计器
```

优点是最接近浪潮标准使用方式，兼容性和平台上下文较好。

缺点是用户可能会进入单独的页面或出现第二个入口，难以满足环宝助手统一入口的产品目标。

### 9.2 方式二：在环宝助手中动态加载原生部件

适合最终产品形态：

```text
环宝 Vue 页面
  -> NativeWidgetHost
  -> 加载 iGIX 运行时脚本
  -> 创建部件实例
  -> 传入配置和当前上下文
  -> 接收部件事件
  -> 转换成环宝助手事件
```

建议新增以下通用模块：

```text
NativeWidgetHost.vue
widgetRegistry.js
widgetLoader.js
widgetLifecycle.js
nativeCapabilityService.js
igixBridge.js
```

这种方式需要逐个验证部件的初始化、销毁、事件和依赖。不能因为脚本路径存在，就直接认定部件可以在任意 iframe 内运行。

### 9.3 方式三：只调用部件背后的平台服务

适合菜单打开、用户读取和平台跳转等能力。

例如菜单打开不一定要显示 `rtfOpenMenu` 的 UI，可以直接调用：

```js
window.top.gspframeworkService.rtf.func.openMenu(options)
```

这种方式可以保留环宝助手自己的视觉体验，同时复用浪潮最成熟的平台动作能力。

## 10. iframe、同源和跨域问题

环宝助手当前运行在 iGIX 门户 iframe 中，原生部件接入必须考虑窗口关系。

### 同源场景

如果助手和 iGIX 门户使用同一个协议、域名和端口，可以尝试直接读取：

```js
window.top.gspframeworkService
```

### 跨域场景

如果助手和门户不是同源，浏览器会阻止 iframe 直接读取父窗口对象。此时需要：

- 环宝助手向父页面发送请求；
- 父页面读取自己的 `gspframeworkService`；
- 父页面将经过白名单过滤的结果回传；
- 菜单打开动作由父页面执行；
- 部件如果依赖 `window.top`，需要单独验证是否能在 iframe 中工作。

### 关键判断

加载 JavaScript 文件本身不代表部件能够正常运行。部件可能还依赖：

- Angular 或平台运行时；
- 特定全局对象；
- 当前门户 DOM 结构；
- 当前用户上下文；
- 平台智能中心配置；
- 特定路由或父页面事件。

因此第一阶段必须在真实门户页面中做运行时 POC。

## 12. 权限和安全要求

### 12.1 不信任模型输出的目标标识

模型可以理解用户说了什么，但不能直接决定：

- 任意菜单 UUID；
- 任意表单字段编码；
- 任意流程实例；
- 任意用户或组织；
- 任意提交动作。

这些内容必须来自可信配置、iGIX 菜单目录或后端校验结果。

### 12.2 菜单权限必须由 iGIX 最终决定

环宝助手可以提供入口推荐，但不能因为识别出了菜单名称，就代表用户有权访问。打开动作必须经过 iGIX 权限体系。

### 12.3 表单动作必须确认

所有写入表单的动作都必须：

- 展示目标表单；
- 展示将要填入的字段和值；
- 允许用户取消；
- 记录字段来源；
- 默认不自动提交；
- 失败时提供明确提示。

### 12.4 角色控制

| 角色 | 默认能力 |
| --- | --- |
| 普通业务用户 | 导航、打开菜单、问答、填单、待办、流程办理、写作 |
| 业务管理员 | 普通用户能力、流程检查和业务配置辅助 |
| 流程设计人员 | 流程绘图、流程优化、流程治理 |
| 平台管理员 | 实体建模、平台配置、权限相关能力 |
| 开发人员 | 代码助手、实体建模、开发调试能力 |

角色控制不能只靠前端隐藏按钮，最终仍需要后端和 iGIX 权限校验。

- `sys / rtfastwelcome`；

- 只保留一个欢迎区；
- 不出现平台第二个全局助手入口；
- 问答对能够配置和展示；
- 快捷问答可以触发环宝能力；

### 13.3 第三批：表单填充

优先验证：

- `rtcommon / fillform`；

- 当前用户信息准确；
- 字段预览准确；
- 用户确认后才填充；
- 不自动提交；
- 填充失败可恢复；
- 明细字段不会被错误覆盖。

### 13.4 第四批：任务和流程

优先验证：

- `task / taskSearch`；
- `workflow / wf`；

- 查询结果只属于当前用户；
- 任务可以准确打开；
- 流程上下文不丢失；

- `bpm / BpmDrawingAIAssistant`；
- `dev / be-designer-widget`；
- `dev / lcmCoderAssistantWidget`；

这些部件需要结合角色、权限、平台开发环境和业务流程验证，不建议作为第一阶段范围。

## 15. 不建议的做法

- 不要把所有部件全部放在环宝助手首页；
- 不要让 `rtfastwelcome` 和 `agentwelcomewidget` 同时展示；
- 不要把 `rtfQaWidget` 直接当成 Dify 完整替代品；
- 不要让模型直接生成并执行任意 `funcId`；
- 不要在前端绕过 iGIX 权限；
- 不要让 `fillform` 默认自动提交；
- 不要把开发类部件暴露给普通业务用户；
- 不要在环宝助手和父页面各执行一次菜单打开；
- 不要将原生部件的运行资源路径误认为公开业务 API；
- 不要在没有确认初始化和销毁协议的情况下批量加载所有部件。
