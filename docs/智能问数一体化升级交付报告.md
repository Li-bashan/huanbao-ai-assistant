# 环宝 AI × Dify 智能问数一体化升级交付报告

更新时间：2026-08-31

## 1. 交付结论

本次代码改造已把智能问数的浏览器入口切换为 AI Gateway；同时已在目标 Dify 实例完成安全版工作流发布：

```text
iGIX 门户 -> 环宝 Vue3 -> POST /api/ai/data-query/chat
          -> AI Gateway 身份/权限/限流/审计
          -> Dify /chat-messages streaming
          -> KingbaseES
          -> Gateway 业务级 SSE
          -> 环宝 v2 协议组件
```

制度问答、办公智能、流程助手和智能填单的原有能力保持独立。Dify 控制台发布已完成；生产密钥配置、Gateway 生产部署、Kingbase 业务回归和 iGIX 现场验证仍必须按本文末尾清单在目标环境执行。

## 2. 修改前架构

智能问数页面直接从浏览器调用 Dify `/chat-messages`，浏览器持有 `VITE_DATA_QUERY_DIFY_API_KEY`，前端静态姓名名单只是 UI 门槛，Dify 工作流直接连接 KingbaseES，结果主要以 Markdown/纯文本返回。

## 3. 修改后职责边界

| 层 | 职责 |
|---|---|
| Dify | 业务意图、Analysis Plan、指标/时间/组织解析、查询计划、SQL 校验、数据库查询、确定性异常和关联证据、Audit JSON、v2 结果组装。 |
| AI Gateway | 隐藏 Dify Key、校验签名身份、查询服务端授权、代理 Dify、转发 conversationId、适配 SSE、统一错误、超时、限流和审计。 |
| 环宝 | 输入、会话生命周期、澄清和追问交互、协议校验、摘要/KPI/表格/图表/洞察渲染、历史、复制和导出。 |

环宝不根据关键词猜 `analysisType`，不重新计算排名/同比，不从摘要文本解析数字，不选择组织 Code。

## 4. Data Query Request Schema

```json
{
  "query": "查询今年项目公司发电量排名",
  "conversationId": "",
  "requestId": "客户端请求 ID",
  "userContext": {
    "userId": "门户用户 ID",
    "userCode": "用户编码",
    "userName": "用户姓名",
    "orgCode": "组织编码",
    "orgName": "组织名称",
    "tenantId": "租户 ID"
  },
  "clientContext": {
    "assistantMode": "data-query",
    "timezone": "Asia/Shanghai",
    "analysisState": "上一轮的结构化分析状态，可为空"
  },
  "clarification": null
}
```

`conversationId` 是环宝持有的用户专属会话句柄，首轮允许为空。Gateway 首轮生成 opaque handle，后续按租户、用户和助手模式校验归属，再使用服务端保存的 Dify `conversation_id` 调用 Dify；Dify 内部会话 ID 不返回浏览器。`userContext` 仅是兼容/试点输入；生产授权以门户签名 Header 解析出的身份和 Gateway 数据库授权为准。

## 5. 身份和权限

Gateway 默认 `DATA_QUERY_IDENTITY_MODE=SIGNED_HEADER`，校验：

- `X-Portal-Identity`
- `X-Portal-Identity-Timestamp`
- `X-Portal-Identity-Signature`
- HMAC-SHA256 签名和时间窗口

随后按 `tenantId + userId` 查询 `ai_data_query_user`，再限制智能问数是否开放、组织范围、指标范围、集团排名和全组织范围。`BODY_TRIAL` 只有显式配置 `DATA_QUERY_ALLOW_BODY_IDENTITY_TRIAL=true` 才能启用，且返回身份标记为未验证；它不是生产安全方案。当前仓库没有假设已经存在完整 iGIX SSO 服务端验签，门户签名桥接和目标环境密钥仍需联调确认。

## 6. Data Query Response Protocol v2

```json
{
  "protocolVersion": "2.0",
  "requestId": "",
  "conversationId": "",
  "status": "SUCCESS_WITH_DATA",
  "messageType": "analysis",
  "analysisType": "RANKING",
  "content": {
    "title": "",
    "summary": "",
    "metrics": [],
    "table": null,
    "chart": null,
    "insights": [],
    "evidence": [],
    "dataInfo": {},
    "followUps": []
  },
  "clarification": null,
  "meta": {}
}
```

支持的 `messageType`：`analysis`、`clarification`、`error`、`empty`、`information`。

支持的 `analysisType`：`FACT`、`DETAIL`、`TREND`、`RANKING`、`COMPARISON`、`RANKING_COMPARISON`、`DISTRIBUTION`、`ANOMALY`、`DRILLDOWN`、`OVERVIEW`。

表格和图表数据必须来自 Dify 确定性 Presentation Model Builder。LLM 只负责受 Audit JSON 约束的摘要和洞察表达。

## 7. SSE 协议

Gateway 对 Dify 内部事件做适配，环宝只依赖这些业务级事件：

| 事件 | 用途 |
|---|---|
| `analysis_started` | 展示正在理解、规划、查询或校验等业务状态。 |
| `text_delta` | 兼容旧版纯文本流；不展示 Dify 节点名。 |
| `analysis_result` | 携带完整 v2 response。 |
| `clarification` | 携带候选组织或指标卡片。 |
| `completed` | 返回最终 conversationId、messageId。 |
| `error` | 返回统一 code/message。 |

Dify 的 `message`、`agent_message`、`workflow_started`、`node_started` 等只在 Gateway/service 层解析。旧版纯文本会包装为 `LEGACY_RESPONSE`，前端显示可信文本降级并记录协议失败标记。

## 8. conversationId 机制

- 新对话：清空当前模式的环宝会话句柄；首轮由 Gateway 创建映射。
- 继续当前会话：只读取 `data-query` 模式的会话句柄。
- 切换助手：制度、办公、智能问数分别维护 ID，互不传递。
- 历史恢复：恢复对应会话的 `conversationIds.data-query`。
- 首轮响应：保存 Gateway 返回的环宝会话句柄，Dify 内部 ID只保存在 Gateway 映射表。
- 连续追问：点击追问或澄清候选时复用同一环宝会话句柄。

本地历史按门户用户命名空间存储，Gateway 仍在每次请求校验当前身份和授权；localStorage 中的 ID 不是权限凭证。

## 9. clarification 机制

Dify 返回：

```json
{
  "messageType": "clarification",
  "status": "CLARIFICATION_REQUIRED",
  "clarification": {
    "slot": "organization",
    "title": "找到多个相关公司，请选择",
    "candidates": [
      {"id": "10004024", "label": "中节能（秦皇岛）环保能源有限公司", "description": ""}
    ]
  }
}
```

环宝渲染可点击候选。点击后把 `selectedValue`、`selectedLabel` 和兼容自然语言 query 通过原 conversationId 发送，不要求领导手工复制 Code，也不创建新会话。

## 10. followUp 机制

`content.followUps` 最多展示少量经过 Dify 当前分析计划生成的动作，例如 `查看后10名`、`和去年同期相比`。点击后只把 `query` 作为下一轮消息发送，保持原 conversationId。

## 11. 环宝组件体系

当前复用 `DataQueryResult` 完成协议驱动渲染，包含：

- Analysis Header 和分析类型标签
- 核心摘要
- KPI Metric Cards
- Schema 驱动的表格，固定表头、横向滚动、数字格式、复制、CSV、最大化
- 统一 ECharts 语义 option
- Insights / Evidence
- 默认折叠的 DataInfo
- Clarification 候选卡片
- FollowUp 操作

compact 默认显示摘要和少量行，wide 显示完整分析块，fullscreen 允许最大化表格。现有门户窗口控制保持不变，不使用 `position: fixed` 破坏 iframe 嵌入。

## 14. Dify 修改节点

`tools/upgrade_dify_enterprise_analysis.js` 已加入确定性的 Presentation Model Builder：从 Audit JSON 生成 `metrics`、`table`、语义 `chart`、`dataInfo`、validated facts 和 `analysisState`，最终 `result_text` 为 v2 JSON。该脚本已在目标 Dify 实例保存并发布，当前工作流为 10 个节点、15 条边；`tools/rebuild_dify_workflow.js` 保留旧工作流重建入口并提供 v2 包装兼容。

脚本不会把 SQL、原始行、数据库凭据或 Dify 技术节点输出给环宝。目标实例的数据库连接凭据仍由 Dify 加密保存。

## 15. 错误、超时和异常降级

Gateway 至少区分：`VALIDATION_ERROR`、`ACCESS_DENIED`、`IDENTITY_UNVERIFIED`、`DATA_QUERY_NOT_COVERED`、`DIFY_UNAUTHORIZED`、`DIFY_TIMEOUT`、`DIFY_ERROR`、`INDICATOR_NOT_FOUND`、`INDICATOR_AMBIGUOUS`、`ORGANIZATION_NOT_FOUND`、`ORGANIZATION_AMBIGUOUS`、`AGGREGATION_NOT_CONFIRMED`、`FORMULA_NOT_FOUND`、`NO_DATA`、`ANALYSIS_FAILED`、`RATE_LIMITED`。

协议字段错误不会让页面崩溃：先保留可信 summary/text，清除损坏的 table/chart，并设置 `PROTOCOL_VALIDATION_FAILED`。Dify 旧版纯文本也降级为 TextMessage。

## 16. 历史兼容

历史消息从 `{role, content}` 扩展为 `messageType`、`analysisType`、`protocol`、`conversationIds`、`createdAt` 等字段。旧消息仍按普通文本渲染；loading/streaming 中间态不入库；结构化表格最多保留受限行数，超大图表和证据会裁剪。

## 17. 审计

Gateway 审计表记录 requestId、用户身份摘要、conversationId、query、analysisType、resolvedIndicator、organizationScope、timeRange、status、duration、dataCutoffDate、Dify request/workflow ID、客户端 IP/UA 和时间。默认不记录完整敏感结果；审计写入失败不会把已成功的用户查询改成失败。

## 20. 必须在目标环境验收的场景

普通单值、趋势、排名、同比、同比排名、多组织比较、指标澄清、组织澄清、连续追问、无数据、无权限、Dify/Gateway 超时、协议错误、历史恢复和三种窗口尺寸。

重点连续追问：

```text
查询今年项目公司发电量排名
只看前5名
秦皇岛排多少
和去年比呢
```

每一轮应核对同一用户的 `conversationId` 能命中同一 Gateway 映射，并核对 Gateway 发给 Dify 的服务端 `conversation_id` 连续一致，不能只核对页面显示。

## 21. 发布步骤

1. 在 Dify 导出并备份现有应用，导入/保存新草稿，确认输入变量和数据源后再发布。
2. 在 Gateway 服务器配置数据库、`DIFY_DATA_QUERY_API_BASE`、`DIFY_DATA_QUERY_API_KEY`、`DATA_QUERY_IDENTITY_SECRET`、CORS、白名单和限流参数；不要写入仓库或前端环境变量。
3. 执行用户授权和审计表迁移，先以最小试点范围启用。
4. 构建并部署 Gateway，再部署环宝静态资源。
5. 在 iGIX iframe 中用签名身份进行完整验收，确认 DevTools 无问数 Dify Key、请求不含 SQL、未授权用户被 Gateway 拒绝。
