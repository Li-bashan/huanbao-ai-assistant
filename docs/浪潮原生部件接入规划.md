# 环宝 AI 助手接入浪潮原生部件规划

更新时间：2026-08-27

## 1. 文档目的

本文用于规划环宝 AI 助手与 iGIX 浪潮平台原生智能部件的整合方式。

目标不是让用户分别使用浪潮平台的多个原生助手入口，而是：

- 用户只看到并使用环宝 AI 助手；
- 环宝助手统一承载欢迎、对话、意图识别和结果展示；
- 浪潮原生部件作为菜单、表单、流程和平台交互能力被环宝助手调用；
- Dify 继续承担制度问答、办公智能和智能问数等知识型能力；
- iGIX 继续承担当前用户、菜单权限、表单打开和平台操作能力。

## 2. 核查结论

### 2.1 浪潮平台具备这些部件

已在部署环境的 iGIX 静态运行目录中发现对应运行文件，说明这些能力已经部署，不需要重新开发平台部件本身。

主要运行路径包括：

```text
/home/GSCloud/web/platform/runtime/sys/web/rtfwidget/
/home/GSCloud/web/platform/runtime/common/web/fillform/
/home/GSCloud/web/platform/runtime/wf/web/
/home/GSCloud/web/platform/runtime/epp/ink/widgets/
```

平台的部件管理页面显示了这些部件，但部件管理页面中存在，不代表某个业务应用已经实际引用它们。

### 2.2 当前环宝助手没有直接使用这些部件

当前环宝助手是 Vue 3 + Vite 项目，以 iframe 的形式嵌入 iGIX 门户。当前源码和项目文档中没有直接引用以下部件编号：

```text
rtf
rtfOpenMenu
rtfQaWidget
rtfastwelcome
agentwelcomewidget
fillform
```

当前项目使用的是自定义 Vue 界面、自定义流程卡片、Dify 接口和 `postMessage` 通信协议。

### 2.3 当前已经使用的 iGIX 能力

当前项目已经接入或设计接入以下平台能力：

1. 通过 `gspframeworkService.common.userInfos.get()` 获取当前登录用户。
2. 在跨域 iframe 场景下，通过 `IGIX_AI_USER_REQUEST` 和 `IGIX_AI_USER_RESPONSE` 获取用户信息。
3. 通过 `IGIX_AI_ACTION` 向门户父页面发送打开表单或菜单的动作。
4. 由门户父页面负责调用 iGIX 的菜单、表单能力。
5. 通过 `IGIX_ASSISTANT_WINDOW` 控制助手的小窗、中窗、全屏和关闭状态。

需要注意：当前环宝助手代码中只包含动作消息发送逻辑，没有发现门户父页面真正消费 `IGIX_AI_ACTION` 并调用 `gspframeworkService.rtf.func.openMenu()` 的实现。因此，当前属于协议已经定义，门户端实际执行逻辑需要单独确认。

## 3. 产品定位

环宝 AI 助手应该成为 iGIX 中唯一的智能入口。

用户不需要知道当前动作到底由 Dify、浪潮原生部件还是 iGIX 服务完成。用户只需要表达业务目标，例如：

```text
帮我打开请假台账
帮我新建一个采购请示单
我有哪些待办任务
这个流程应该怎么走
帮我把表单中的联系人填成当前用户
这个流程图有没有问题
```

环宝助手根据用户意图选择底层能力：

```text
用户
  -> 环宝助手对话入口
  -> 意图识别和参数提取
  -> 原生部件适配层或 Dify 能力
  -> iGIX 权限和平台服务
  -> 在环宝助手中展示结果
```

产品原则是：

- 一个入口；
- 一个对话上下文；
- 多种底层能力；
- 按场景懒加载；
- 权限始终由 iGIX 控制；
- 高风险操作必须确认；
- 原生部件不可用时要有降级方案。

## 4. 原生部件能力地图

### 4.1 普通用户优先使用的能力

#### `sys / rtf` 框架智能导航

定位：平台菜单树、功能发现和框架级导航。

建议用途：

- 用户不知道菜单准确名称时，展示可访问的菜单候选；
- 按业务模块展示菜单、台账、看板；
- 提供环宝助手的功能导航结果；
- 减少人工维护大量菜单名称和入口关系。

注意：仅仅让大模型输出菜单编号是不安全的。应优先从 iGIX 当前用户可访问的菜单树或菜单查询能力中解析目标，再调用打开操作。

#### `sys / rtfOpenMenu` 菜单智能导航

定位：打开菜单、台账、看板等平台功能。

这是第一优先级接入能力。它可以减少环宝助手自己编写菜单打开界面的工作量。

如果组件方式无法直接嵌入，也可以调用它背后的 iGIX 框架服务：

```js
const root = window.top || window

root.gspframeworkService.rtf.func.openMenu({
  appType: 'menu',
  funcId: '菜单功能UUID',
  appId: '',
  appEntrance: '',
  isNewTab: true,
  tabId: `ai_${Date.now()}`
})
```

`funcId` 应使用菜单的 UUID。菜单编号或菜单代码可以用于识别和日志记录，但不能代替平台要求的功能 UUID。

例如此前的 `LeaveOpsList` 菜单可以使用：

```js
root.gspframeworkService.rtf.func.openMenu({
  appType: 'menu',
  funcId: '193545d8-29f9-4790-99f0-6c517aca3e4f',
  appId: '',
  appEntrance: '',
  isNewTab: true,
  tabId: `LeaveOpsList_${Date.now()}`
})
```

#### `sys / rtfClarification` 应用澄清

定位：用户表达不明确时帮助用户选择正确的应用、菜单或业务对象。

建议接入在菜单打开之前。例如用户说打开请假，系统发现请假申请、请假台账和请假审批三个入口时，先展示澄清结果，而不是猜一个入口直接打开。

#### `rtcommon / fillform` 智能填单助手

定位：根据用户输入和当前用户上下文，对 iGIX 表单执行字段填充。

建议接入到表单场景，但必须采用确认式交互：

```text
识别用户意图
  -> 展示待填字段和字段值
  -> 用户确认
  -> 调用 fillform
  -> 打开或刷新表单
  -> 禁止自动提交
```

当前项目中的 `ENABLE_WORKFLOW_PREFILL = false`，说明原项目有预填解析能力但主动关闭了。接入 `fillform` 后需要重新验证字段编码、表单上下文、权限和异常回滚。

#### `sys / modifyformmessage` 智能组件操作确认按钮

定位：表单填充、修改或智能操作前后的确认控制。

建议与 `fillform` 配套使用，统一处理：

- 即将填充哪些字段；
- 哪些字段来自当前用户信息；
- 哪些字段来自用户自然语言；
- 哪些字段无法识别；
- 用户是否确认执行。

#### `task / taskSearch` 工作流任务查询部件

定位：待办、已办、待阅和流程任务查询。

建议接入为任务类意图的首选能力，例如：

```text
我有哪些待办
需要我审批的单据
最近有哪些流程退回
```

#### `workflow / wf` 工作流智能助手

定位：流程办理和工作流相关的智能辅助能力。

建议在用户明确进入流程办理场景时加载，不建议首页常驻。

### 4.2 特定角色或专业场景使用的能力

#### `sys / rtfQaWidget` 问答对部件

定位：问答对、固定问答或快捷问题能力。

它不应直接被当作现有 Dify 对话的替代品。建议作为以下能力使用：

- 常用问题快捷入口；
- 固定制度问答；
- 业务操作提示；
- 结构化的快捷指令。

自由问答、制度知识检索、办公写作和智能问数仍由 Dify 负责，除非后续验证该部件可以接入现有知识源和对话协议。

#### `sys / rtfastwelcome` 助手欢迎部件

定位：助手欢迎页、能力入口或常用操作推荐。

建议和现有自定义欢迎页进行对比测试后选择一个作为环宝助手欢迎区，不建议两套欢迎界面同时出现。

#### `sys / agentwelcomewidget` 智能体开屏欢迎部件

定位：智能体开屏、智能体推荐或智能服务入口。

它和 `rtfastwelcome` 的职责有重叠，需要先确认两个部件的实际参数和渲染效果。产品上只保留一个主欢迎部件，另一个作为备用或特定场景部件。

#### `bpm / BpmDrawingAIAssistant` 业务流智能绘图助手

定位：业务流程图生成、调整或辅助设计。

只向流程设计人员、业务管理员或开发人员提供，不应默认展示给普通业务用户。

#### `checkWorkFlowChart / checkWorkFlow` 工作流智能优化助手

定位：流程检查、流程优化和问题诊断。

可以由用户提出流程优化问题时按需加载，也可以在流程设计页面上下文中显示。

#### `dev / be-designer-widget` 智能实体建模

定位：业务实体、模型和低代码开发辅助。

属于开发和管理员能力，应根据角色权限控制，不进入普通用户的默认能力列表。

#### `dev / lcmCoderAssistantWidget` 智能代码助手

定位：代码生成、解释和开发辅助。

只对开发人员开放，并且要与开发环境、代码权限和敏感代码保护策略配套。

#### `ink / inkOutliner` 智能写作大纲

定位：写作、材料组织和大纲生成。

可以作为办公智能的一个专用工具，在用户需要写材料时按需加载。

## 5. 推荐的整体架构

现有 Vue 项目保留为环宝助手外壳，在其中增加统一的原生部件适配层。

```text
src/
  components/
    NativeWidgetHost.vue
    NativeWidgetFallback.vue
  platform/
    widgetRegistry.js
    widgetLoader.js
    widgetLifecycle.js
    igixBridge.js
    menuResolver.js
    permissionGuard.js
  services/
    intentOrchestrator.js
    nativeCapabilityService.js
  config/
    nativeWidgets.js
    capabilityPolicies.js
```

### 5.1 `NativeWidgetHost`

职责：

- 创建独立 DOM 容器；
- 按需加载浪潮运行时 JavaScript；
- 初始化指定命名空间和部件编号；
- 传入部件配置和用户上下文；
- 监听部件事件；
- 组件切换或页面销毁时执行清理；
- 部件加载失败时展示环宝助手自己的降级界面。

这些部件不能默认按照 Vue 组件直接 `import`。需要通过运行时脚本加载和平台部件宿主机制进行适配。第一阶段必须用真实门户环境验证初始化接口和销毁接口。

### 5.2 `widgetRegistry`

统一登记原生部件：

```js
{
  key: 'open-menu',
  namespace: 'sys',
  code: 'rtfOpenMenu',
  script: '/platform/runtime/sys/web/rtfwidget/rtfopenmenu.js',
  capability: 'navigation.open-menu',
  roles: ['all'],
  lazy: true,
  requiresConfirm: false
}
```

登记表中应保存：

- 命名空间；
- 部件编号；
- 运行资源路径；
- 适用场景；
- 适用角色；
- 是否懒加载；
- 是否需要确认；
- 是否允许降级；
- 当前验证状态。

### 5.3 `igixBridge`

统一处理：

- 当前用户读取；
- 菜单打开；
- 表单打开；
- 部件事件转发；
- 父页面通信；
- 当前门户 origin；
- 动作幂等和审计。

现有的 `getIgixCurrentUser()` 和 `sendIgixAction()` 可以作为这个适配层的基础，不建议在新的部件中重复读取用户或重复发送消息。

### 5.4 `intentOrchestrator`

用户输入先转成结构化意图，再选择底层能力：

```text
intent: navigation.open_menu
target: LeaveOpsList
funcId: 193545d8-29f9-4790-99f0-6c517aca3e4f
requiresConfirm: false
```

或：

```text
intent: form.fill
formCode: CGQSD
fields:
  联系人: 当前用户姓名
  联系电话: 当前用户手机号
requiresConfirm: true
```

大模型可以负责理解用户语言，但不能直接决定任意菜单 UUID、任意字段编码或任意提交动作。目标必须来自可信的平台配置、菜单目录或后端返回结果。

## 6. 用户使用流程

### 6.1 用户打开菜单

```text
用户：帮我打开请假台账
  -> 环宝助手识别为菜单导航
  -> rtf 或菜单解析服务查询可访问入口
  -> 如果存在多个结果，调用 rtfClarification
  -> 用户确认目标入口
  -> rtfOpenMenu 或 gspframeworkService.rtf.func.openMenu
  -> iGIX 按当前用户权限打开菜单
```

### 6.2 用户填充表单

```text
用户：帮我新建采购请示单，项目叫污水处理改造，联系人用我自己
  -> 环宝助手识别为表单填充
  -> 读取当前用户白名单信息
  -> 解析项目名称和联系人
  -> 展示字段确认卡
  -> 用户确认
  -> fillform 执行填充
  -> 打开表单
  -> 用户自行检查和提交
```

### 6.3 用户查询任务

```text
用户：我有哪些待办
  -> 识别为工作流任务查询
  -> 加载 taskSearch
  -> 展示待办结果
  -> 用户点击任务后由 iGIX 打开对应流程
```

### 6.4 用户提出知识问题

```text
用户：公司的出差报销标准是什么
  -> 识别为制度问答
  -> 调用 Dify 制度问答应用
  -> 展示答案和引用来源
```

## 7. 接入优先级

### 第一阶段：验证原生部件能否嵌入环宝助手

只做最小可行验证：

1. 加载 `rtfOpenMenu`。
2. 打开已知的 `LeaveOpsList` 菜单。
3. 验证门户页面、iframe 页面和部件之间的窗口关系。
4. 验证菜单打开后是否重复打开。
5. 验证权限仍由 iGIX 控制。
6. 验证部件销毁后再次打开不会重复注册事件。

这一阶段成功后，才能确定采用组件嵌入方式，还是采用平台服务适配方式。

### 第二阶段：接入普通用户核心能力

优先接入：

- `rtf`；
- `rtfOpenMenu`；
- `rtfClarification`；
- `rtfQaWidget`；
- `rtfastwelcome` 或 `agentwelcomewidget`，二选一。

目标是让用户可以通过环宝助手发现功能、澄清目标、打开菜单，并看到统一的欢迎区。

### 第三阶段：接入表单智能化

接入：

- `fillform`；
- `modifyformmessage`。

必须先完成字段映射、字段来源展示、用户确认、异常提示和不自动提交验证。

### 第四阶段：接入流程和任务能力

接入：

- `taskSearch`；
- `wf`；
- `checkWorkFlow`。

根据用户是否处于待办、流程办理或流程设计上下文，按需加载不同部件。

### 第五阶段：接入专业角色能力

接入：

- `BpmDrawingAIAssistant`；
- `be-designer-widget`；
- `lcmCoderAssistantWidget`；
- `inkOutliner`。

这些部件只在角色允许并且用户明确提出相关需求时出现。

## 8. 入口和展示策略

虽然这些部件全部接入，但不能全部同时展示。

环宝助手首页建议只保留：

- 一个欢迎区；
- 一个对话区；
- 少量常用能力入口；
- 当前用户允许使用的快捷功能。

其他能力根据用户意图在对话中出现。

建议平台侧关闭或隐藏原生的全局智能助手入口，避免以下问题：

- 两个欢迎入口同时出现；
- 浪潮助手和环宝助手同时弹出；
- 同一个菜单被打开两次；
- 用户不知道应该使用哪个入口；
- 两套对话历史和上下文相互割裂。

平台原生部件可以继续部署和调用，但不应该继续作为独立的用户入口展示。

## 9. 权限、安全和审计

### 9.1 权限

- 菜单打开最终必须经过 iGIX 权限控制；
- 部件的角色范围必须和 iGIX 用户角色一致；
- 不能通过环宝助手绕过菜单权限；
- Dify 返回的菜单或表单标识必须经过可信配置校验；
- 开发类部件不能对普通用户开放。

### 9.2 iframe 通信

生产环境不能长期使用 `postMessage(..., '*')`。

应当：

- 配置明确的门户 origin；
- 校验 `event.origin`；
- 校验 `event.source` 是否为预期 iframe；
- 对用户信息请求设置 requestId；
- 对动作消息设置唯一 actionId；
- 对重复 actionId 做幂等处理。

### 9.3 表单操作

- 填充前展示字段和值；
- 用户确认后才执行；
- 默认不自动提交；
- 不把不可信的自然语言直接当作字段编码；
- 记录字段来源和执行结果；
- fillform 不可用时降级为普通打开表单。

### 9.4 审计

至少记录：

- 当前用户标识；
- 用户原始输入；
- 识别出的能力；
- 目标菜单或表单；
- funcId 或 formCode；
- 是否经过澄清；
- 是否经过用户确认；
- actionId；
- 部件执行结果；
- 失败原因。

## 10. 当前项目需要保留和调整的内容

### 建议保留

- Vue 3 + Vite 项目外壳；
- 环宝助手 Header、ChatBody 和 Footer；
- Dify 制度问答；
- Dify 办公智能；
- Dify 智能问数；
- 当前用户读取和跨域桥接；
- iframe 窗口控制；
- actionId 和审计设计；
- 错误提示和降级界面。

### 建议重构

- 将现有流程入口识别改造成统一意图编排层；
- 将手工菜单映射逐步替换为平台菜单解析和可信配置；
- 将自定义的菜单打开逻辑替换成原生部件或 iGIX 服务适配器；
- 将自定义欢迎区改造成原生欢迎部件的宿主容器；
- 将表单预填解析接入 `fillform`，但保留人工确认；
- 将流程和待办能力改造成按需加载的原生能力模块。

当前项目中的流程映射只有采购请示单处于 `verified`，其他入口大多处于 `pending`。本规划允许重新设计这部分流程，但任何入口在正式开放前仍需在真实 iGIX 环境中逐项验证。

## 11. 验收标准

### 单一入口

- 用户只看到环宝助手；
- 平台原生入口不会和环宝助手重复出现；
- 所有原生部件均从环宝助手内部进入。

### 菜单导航

- 可以通过自然语言找到菜单；
- 多个候选时可以澄清；
- 已知菜单可以准确打开；
- 不重复打开；
- 无权限菜单不能被打开。

### 智能填单

- 可以读取当前登录用户白名单字段；
- 可以识别用户明确提供的字段；
- 执行前展示字段确认；
- 不自动提交；
- 失败时不会破坏原表单数据。

### 流程和待办

- 可以查询当前用户任务；
- 可以从任务打开对应 iGIX 页面；
- 流程设计类部件只对允许角色显示；
- 普通用户不会看到开发和流程设计工具。

### 稳定性

- 原生部件运行时按需加载；
- 加载失败有降级界面；
- 页面切换后部件事件被正确清理；
- 生产环境使用明确 origin；
- 所有重要动作可通过 actionId 追踪。

## 12. 最终决策建议

建议采用以下产品和技术决策：

1. 环宝助手作为唯一用户入口。
2. `rtf`、`rtfOpenMenu`、`rtfClarification` 作为菜单导航核心能力。
3. `fillform` 和 `modifyformmessage` 作为智能填单核心能力。
4. `taskSearch`、`wf` 和 `checkWorkFlow` 作为流程能力。
5. `rtfQaWidget` 作为固定问答和快捷问题能力，不立即替换 Dify。
6. `rtfastwelcome` 与 `agentwelcomewidget` 先验证后选一个。
7. 代码助手、实体建模、流程绘图和智能写作按角色及场景懒加载。
8. 保留 Dify 作为知识问答和自然语言理解能力。
9. 保留 iGIX 权限体系，不在前端自行判断最终权限。
10. 优先完成 `rtfOpenMenu` 的真实门户 POC，再扩展其他部件。

最终形态不是把所有部件堆在一起，而是让环宝助手成为统一调度层：用户只需要和环宝助手说话，底层能力由最合适的浪潮部件、iGIX 服务或 Dify 应用完成。
